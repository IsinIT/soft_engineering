# Часть I. Непрерывная интеграция

## 1. Цели лекции и план

После лекции студент должен **знать**:

- что такое CI и чем он отличается от CD (Delivery / Deployment);
- из каких этапов состоит типичный пайплайн и в каком порядке они идут;
- основные понятия GitHub Actions: workflow, event, job, step, runner, action;
- что такое кэш, артефакт, матрица сборки, секрет;
- что такое OpenAPI и как устроен файл `openapi.yaml`;
- чем отличаются моки, заглушки и реальный сервер;
- какие бывают виды контрактного тестирования.

И **уметь**:

- описать пайплайн «Checkout → Lint → Test → Build → Upload Artifact» в YAML;
- сделать так, чтобы красный пайплайн блокировал слияние;
- описать REST API в формате OpenAPI;
- запустить мок-сервер по спецификации;
- написать автотесты, проверяющие, что API соответствует контракту.

**Ход лекции:**

| Блок | Время |
|---|---|
| CI: идея, этапы пайплайна | 15 мин |
| GitHub Actions и GitLab CI | 20 мин |
| OpenAPI, design-first, инструменты | 20 мин |
| Моки и контрактное тестирование | 20 мин |
| Совместимость API, CI для контракта, итоги | 15 мин |

## 2. Что такое CI и зачем он нужен

### 2.1. Проблема, с которой всё начиналось

Представьте команду из пяти человек, которая неделю работает в своих ветках и в пятницу сливает всё вместе:

- код одного ломает код другого («integration hell»);
- никто не знает, какая именно правка сломала сборку;
- «у меня на компьютере работает» — но не у остальных;
- релиз откладывается, потому что неделю уходит на исправление конфликтов.

### 2.2. Определение

**Continuous Integration (CI, непрерывная интеграция)** — практика, при которой разработчики **часто** (минимум раз в день) интегрируют свои изменения в общую ветку, а каждое изменение **автоматически** собирается и проверяется на сервере.

Ключевая идея: **ошибки интеграции дешевле находить сразу, чем накапливать**.

### 2.3. CI, Continuous Delivery и Continuous Deployment

| Термин | Что автоматизировано | Что делает человек |
|---|---|---|
| **CI** (Integration) | Сборка и проверка каждого изменения | Пишет код, смотрит на результат |
| **Continuous Delivery** | CI + подготовка релиза, который **можно** выпустить в любой момент | Нажимает кнопку «выпустить» |
| **Continuous Deployment** | CI + автоматический выпуск каждого успешного изменения в продакшен | Следит за мониторингом |

```
 Код ──► Сборка ──► Тесты ──► Артефакт ──► Staging ──► Production
 └──────────── CI ────────────┘
 └──────────────── Continuous Delivery ────────────────┘ (ручное решение)
 └──────────────── Continuous Deployment ────────────────────────► (автоматически)
```

В этой лекции и практической работе мы строим **CI** и заканчиваем получением **артефакта сборки**.

### 2.4. Практики CI

1. Единый репозиторий с основной веткой (`main`).
2. **Сборка автоматизирована** одной командой.
3. **Тесты автоматизированы** и входят в сборку.
4. Каждый push и каждый Pull Request запускает пайплайн.
5. **Быстрая обратная связь:** пайплайн занимает минуты, а не часы.
6. Сломанную основную ветку чинят **в первую очередь**.
7. Результат виден всем (статус в PR, значок в README).

## 3. Анатомия пайплайна: Checkout → Lint → Test → Build → Upload

**Пайплайн (pipeline)** — последовательность автоматических этапов (stages/jobs), через которые проходит каждое изменение кода.

### 3.1. Типичная схема

```
┌──────────┐   ┌──────┐   ┌──────┐   ┌───────┐   ┌─────────────────┐
│ Checkout │──►│ Lint │──►│ Test │──►│ Build │──►│ Upload Artifact │
└──────────┘   └──────┘   └──────┘   └───────┘   └─────────────────┘
 получить      стиль и    unit,       собрать       сохранить результат
 код           статика    контракт    пакет         для скачивания/деплоя
```

### 3.2. Что делает каждый этап

| Этап | Задача | Примеры команд | Если упал |
|---|---|---|---|
| **Checkout** | Получить исходный код нужного коммита | `actions/checkout` | Дальше идти нельзя |
| **Setup** | Подготовить окружение (Node, Python, JDK), восстановить кэш | `actions/setup-node` | Среда не готова |
| **Install** | Установить зависимости **по lock-файлу** | `npm ci`, `pip install -r` | Проблема зависимостей |
| **Lint** | Форматирование, линтер, проверка спецификации | `eslint`, `spectral lint` | Нарушены правила |
| **Test** | Unit-, интеграционные, контрактные тесты | `jest`, `pytest` | Функциональная ошибка |
| **Build** | Сборка проекта в готовый к поставке вид | `npm run build`, `mvn package` | Не собирается |
| **Upload Artifact** | Сохранить результат сборки и отчёты | `actions/upload-artifact` | Результат потерян |

### 3.3. Принцип fail fast (падай быстро)

Порядок этапов выбирают так, чтобы **дешёвые и быстрые проверки шли первыми**:

```
Линтер (10 с)  →  Unit-тесты (30 с)  →  Контрактные (1 мин)  →  Сборка (2 мин)
```

Если линтер нашёл ошибку, нет смысла ждать 5 минут сборки: разработчик узнаёт о проблеме через 10 секунд.

### 3.4. Последовательность и параллельность

- Этапы с зависимостью выполняются **последовательно** (сборка после тестов).
- Независимые проверки (линтер и тесты) можно запускать **параллельно** — общее время падает.

```
        ┌──► lint ──┐
push ──►│           ├──► build ──► upload
        └──► test ──┘
```

### 3.5. Воспроизводимость

Пайплайн должен давать **один и тот же результат** на одном и том же коммите:

- зафиксированные версии зависимостей (`package-lock.json`);
- `npm ci`, а не `npm install`;
- закреплённая версия Node.js/JDK/Python;
- чистое окружение при каждом запуске (runner создаётся заново).

## 4. GitHub Actions: основные понятия

**GitHub Actions** — встроенная в GitHub система автоматизации. Конфигурация хранится **в репозитории** в каталоге `.github/workflows/` в виде YAML-файлов.

### 4.1. Терминология

| Понятие | Что это |
|---|---|
| **Workflow** | Один YAML-файл: автоматизированный процесс (например, `ci.yml`) |
| **Event** (событие) | То, что запускает workflow: `push`, `pull_request`, `schedule`, `workflow_dispatch` |
| **Job** | Набор шагов, выполняемых на одном runner. Разные jobs по умолчанию идут параллельно |
| **Step** (шаг) | Отдельная команда (`run`) или готовое действие (`uses`) |
| **Action** | Готовый переиспользуемый блок (`actions/checkout@v4`) |
| **Runner** | Машина, на которой выполняется job (`ubuntu-latest`, `windows-latest`, `macos-latest` или self-hosted) |
| **Artifact** | Файлы, сохранённые по итогам запуска |
| **Secret** | Зашифрованное значение (токен, пароль), недоступное в логах |

### 4.2. Иерархия

```
Repository
 └── .github/workflows/ci.yml           ← Workflow
       ├── on: push, pull_request       ← Events
       └── jobs:
             ├── lint   (runner #1)     ← Job
             │     └── steps: checkout → setup → install → eslint
             ├── test   (runner #2)     ← Job
             └── build  (runner #3)     ← Job (needs: lint, test)
```

**Важно:** каждый job выполняется на **отдельной** чистой виртуальной машине. Файлы между jobs автоматически **не передаются** — для этого нужны артефакты или кэш.

### 4.3. Минимальный workflow

```yaml
name: CI                     # имя в интерфейсе

on:                          # когда запускать
  push:
    branches: [main]
  pull_request:

jobs:
  hello:
    runs-on: ubuntu-latest   # на чём запускать
    steps:
      - uses: actions/checkout@v4          # готовое действие
      - run: echo "Hello, CI!"             # shell-команда
```

### 4.4. События (`on`)

| Событие | Когда срабатывает |
|---|---|
| `push` | Новые коммиты отправлены в репозиторий (можно ограничить ветками/путями) |
| `pull_request` | Открытие, обновление PR; код проверяется **в результате слияния** с целевой веткой |
| `workflow_dispatch` | Ручной запуск кнопкой |
| `schedule` | По расписанию (cron) |
| `release` | Публикация релиза |

Фильтры по путям экономят ресурсы:

```yaml
on:
  pull_request:
    paths:
      - 'src/**'
      - 'openapi.yaml'
      - 'package*.json'
```

### 4.5. Условия и зависимости

```yaml
jobs:
  build:
    needs: [lint, test]            # запустится только если lint и test успешны
    if: github.event_name == 'push' # необязательное условие
```

Шаг можно сделать «всегда выполняемым» (например, чтобы выгрузить отчёт даже при падении тестов):

```yaml
- uses: actions/upload-artifact@v4
  if: always()
```

### 4.6. Контекст и переменные

Внутри workflow доступны выражения `${{ ... }}`:

| Выражение | Значение |
|---|---|
| `${{ github.sha }}` | Хэш коммита |
| `${{ github.ref_name }}` | Имя ветки или тега |
| `${{ github.actor }}` | Кто запустил |
| `${{ github.event_name }}` | Тип события |
| `${{ secrets.NAME }}` | Секрет |
| `${{ vars.NAME }}` | Несекретная переменная конфигурации |
| `${{ runner.os }}` | ОС runner |

## 5. Пример workflow по этапам

Файл `.github/workflows/ci.yml` для проекта на Node.js:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read              # принцип минимальных прав

concurrency:                  # отменять устаревшие запуски той же ветки
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    name: lint
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm                 # кэш зависимостей

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

  test:
    name: test
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: Test
        run: npm test -- --coverage

      - name: Upload coverage report
        if: always()                 # отчёт нужен и когда тесты упали
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/
          if-no-files-found: ignore

  build:
    name: build
    needs: [lint, test]              # сборка только после успешных lint и test
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: Build
        run: npm run build

      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: app-${{ github.sha }}
          path: dist/
          retention-days: 7
          if-no-files-found: error   # нет файлов = ошибка
```

> Номера версий действий (`@v4`) даны для примера; перед использованием проверьте актуальные версии на страницах действий.

### Как это читать

1. На каждый `push` в `main` и каждый Pull Request запускаются **три job**.
2. `lint` и `test` идут **параллельно**.
3. `build` стартует, **только если** оба успешны (`needs`).
4. После сборки каталог `dist/` сохраняется как **артефакт** с именем, включающим хэш коммита: по нему можно точно сказать, из какого кода собран файл.

## 6. Кэш, артефакты, матрица, секреты

### 6.1. Кэш и артефакт — не одно и то же

| | Кэш (cache) | Артефакт (artifact) |
|---|---|---|
| Зачем | **Ускорить** повторные запуски | **Сохранить результат** работы |
| Что хранит | Зависимости (`~/.npm`, `~/.m2`) | Сборка, отчёты, логи, документацию |
| Ключ | Хэш lock-файла | Имя артефакта |
| Доступ человека | Нет | Можно скачать со страницы запуска |
| Можно потерять без последствий | Да (будет просто медленнее) | Нет, это результат |

### 6.2. Артефакты

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: app-build
    path: dist/
    retention-days: 7
```

Скачать в другом job:

```yaml
- uses: actions/download-artifact@v4
  with:
    name: app-build
    path: dist/
```

Типичные артефакты: собранный пакет (`.jar`, архив), отчёт о покрытии, отчёты тестов, HTML-документация API, скриншоты упавших UI-тестов.

> Артефакты занимают место и имеют срок хранения. Задавайте `retention-days` и не выгружайте лишнего (например, `node_modules`).

### 6.3. Матрица сборки

Позволяет прогнать задачу на нескольких версиях/платформах:

```yaml
strategy:
  fail-fast: false
  matrix:
    node: [20, 22]
    os: [ubuntu-latest, windows-latest]
steps:
  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node }}
```

Получится 4 параллельных запуска. Имена проверок будут вида `test (20, ubuntu-latest)`; помните об этом при настройке обязательных проверок в защите ветки.

### 6.4. Секреты и переменные

- **Secrets** — пароли, токены. Хранятся зашифрованно: *Settings → Secrets and variables → Actions*.
- В логах значения секретов маскируются (`***`), но **нельзя** выводить их частями или в преобразованном виде.
- Секреты не передаются в workflow для Pull Request **из форков** (защита от кражи).
- **Variables** — несекретная конфигурация (например, адрес тестового окружения).

```yaml
env:
  API_URL: ${{ vars.API_URL }}
steps:
  - run: ./deploy.sh
    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

## 7. GitLab CI: то же самое другими словами

В GitLab конфигурация лежит в **одном** файле `.gitlab-ci.yml` в корне репозитория.

### 7.1. Соответствие понятий

| GitHub Actions | GitLab CI |
|---|---|
| Workflow (`.github/workflows/*.yml`) | Pipeline (`.gitlab-ci.yml`) |
| Job | Job |
| Порядок через `needs` | Порядок через **`stages`** (и `needs`) |
| `runs-on` | `image` (Docker-образ) + runner |
| `uses: action` | `script` / `include` / шаблоны |
| `actions/upload-artifact` | `artifacts:` внутри job |
| `actions/cache` | `cache:` |
| Secrets | CI/CD Variables (Masked/Protected) |
| Required status checks | *Pipelines must succeed* в настройках merge request |
| Pull Request | Merge Request |

### 7.2. Пример

```yaml
image: node:20

stages:
  - lint
  - test
  - build

cache:
  key:
    files:
      - package-lock.json
  paths:
    - .npm/

variables:
  npm_config_cache: "$CI_PROJECT_DIR/.npm"

before_script:
  - npm ci

lint:
  stage: lint
  script:
    - npm run lint

test:
  stage: test
  script:
    - npm test -- --coverage
  artifacts:
    when: always
    paths:
      - coverage/
    expire_in: 7 days

build:
  stage: build
  script:
    - npm run build
  artifacts:
    name: "app-$CI_COMMIT_SHORT_SHA"
    paths:
      - dist/
    expire_in: 7 days
```

Особенность: jobs одной стадии идут параллельно, следующая стадия стартует после успешного завершения предыдущей.

### 7.3. Сравнение подходов

| Критерий | GitHub Actions | GitLab CI |
|---|---|---|
| Модель | Набор workflow + marketplace действий | Единый конфиг + встроенная платформа |
| Переиспользование | Actions, reusable workflows | `include`, `extends`, шаблоны |
| Хостинг runner'ов | GitHub-hosted или self-hosted | GitLab shared runners или свои |
| Сильные стороны | Огромный каталог готовых действий | Тесная интеграция DevOps-инструментов в одной платформе |

Идеи одинаковые, отличается синтаксис. Освоив один инструмент, вы быстро освоите второй. Существуют и другие системы: Jenkins, CircleCI, TeamCity, Azure Pipelines.

## 8. Принципы хорошего пайплайна и безопасность

### 8.1. Принципы

| Принцип | Что значит |
|---|---|
| **Быстрый** | Целевое время — единицы минут; медленный CI обходят |
| **Надёжный** | Падает только по реальной причине; нестабильные («flaky») тесты чинят или изолируют |
| **Воспроизводимый** | `npm ci`, закреплённые версии, чистая среда |
| **Информативный** | По логу понятно, что и почему упало |
| **Как код** | Конфиг в репозитории, меняется через PR |
| **Один источник правды** | Те же команды, что запускает разработчик локально (`npm run lint`, `npm test`) |
| **Минимум прав** | `permissions: contents: read`, только необходимые секреты |

> **Совет:** в пайплайне вызывайте **скрипты проекта** (`npm run lint`), а не длинные команды. Тогда локальный запуск и CI гарантированно совпадают.

### 8.2. Безопасность

1. **Не храните секреты в репозитории** и не печатайте их в лог.
2. **Закрепляйте версии действий.** Для максимальной защиты — по полному хэшу коммита (`uses: owner/action@<sha>`), так как тег можно переместить. Минимум — по мажорной версии из надёжных источников.
3. **Ограничивайте `permissions`** токена `GITHUB_TOKEN`.
4. **Осторожно с `pull_request_target`:** это событие запускается с доступом к секретам и может выполнить недоверенный код из форка. Для проверки внешних PR используйте `pull_request`.
5. **Не подставляйте недоверенные данные** (заголовок PR, имя ветки) напрямую в команды shell: возможна инъекция команд.

### 8.3. Типичные причины красного CI

| Симптом | Причина |
|---|---|
| Локально работает, в CI нет | Разные версии Node/зависимостей, забыт файл, зависимость от окружения |
| `npm ci` падает | `package.json` и `package-lock.json` рассогласованы |
| Тесты «моргают» | Зависимость от времени, порядка, сети, общего состояния |
| Лимит времени | Нет кэша, лишние шаги, слишком тяжёлые тесты |
| Нет прав | Не задан секрет или ограничены `permissions` |

## 9. Блокировка merge и статус сборки

Сам по себе красный CI **не запрещает** слить PR. Запрет создаёт настройка защиты ветки.

В GitHub: *Settings → Rules → Rulesets* (или *Branches → Branch protection*):

- Require a pull request before merging;
- Require status checks to pass → выбрать `lint`, `test`, `build`;
- Require branches to be up to date before merging.

В GitLab: *Settings → Merge requests → Pipelines must succeed*.

Результат: пока пайплайн красный или не завершён, кнопка **Merge** неактивна.

```
Push в ветку ──► CI ──► зелёный ──► Merge разрешён
                  └───► красный ──► Merge заблокирован ──► исправить ──► новый запуск
```

**Итог части I:** автоматическая сборка и проверка при каждом Push/PR + обязательный статус перед слиянием = основа дисциплины качества в команде.

# Часть II. API и контрактное тестирование

## 10. Зачем нужен контракт API

### 10.1. Типичная история

Backend-разработчик и frontend-разработчик договорились «на словах»: «возвращай список аудиторий». Через неделю:

- backend называет поле `capacity`, а frontend ждёт `seats`;
- backend возвращает `id` числом, frontend сравнивает как строку;
- для «не найдено» backend отдаёт 200 с пустым телом, а frontend ждёт 404;
- пока backend не готов, frontend не может проверить свою часть.

Всё это обнаруживается **поздно**, при интеграции.

### 10.2. Контракт

**Контракт API** — формальное, машиночитаемое описание того, как устроен интерфейс: адреса, методы, параметры, форматы запросов и ответов, коды ошибок.

Контракт отвечает на вопросы «что я отправляю?» и «что получу в ответ?» и служит **единым источником правды** для:

- документации;
- разработки клиента и сервера параллельно;
- генерации моков и клиентских библиотек;
- автоматической проверки, что сервер соблюдает договорённость.

```
                  ┌────────────────┐
                  │  openapi.yaml  │  ← единый источник правды
                  └───────┬────────┘
        ┌─────────┬───────┼─────────┬──────────────┐
        ▼         ▼       ▼         ▼              ▼
   Документация  Мок   Клиент/типы  Контрактные   Проверка
   (Swagger UI) сервер  (генерация) тесты сервера  совместимости
```

## 11. OpenAPI: структура описания

### 11.1. История и версии

- **Swagger** — изначальное название спецификации и инструментов (SmartBear).
- В 2015 году спецификацию передали Linux Foundation, она получила название **OpenAPI Specification (OAS)**.
- «Swagger» теперь обозначает набор инструментов (Swagger Editor, Swagger UI), а не формат.

Версии: 2.0 (старое название Swagger 2.0), **3.0.x** (самая распространённая), **3.1** (согласована с JSON Schema 2020-12). В практической работе используется **3.0.3**: её поддерживает большинство инструментов.

Формат — **YAML** или JSON.

### 11.2. Структура документа

```yaml
openapi: 3.0.3          # версия спецификации
info:                   # сведения об API
servers:                # адреса серверов
tags:                   # группы операций
paths:                  # ЭНДПОИНТЫ — главная часть
components:             # переиспользуемые схемы, ответы, параметры
```

| Раздел | Назначение |
|---|---|
| `info` | Название, версия API, описание, контакты, лицензия |
| `servers` | Базовые адреса (локальный, тестовый, мок, продакшен) |
| `tags` | Группировка операций в документации |
| `paths` | Адреса и методы с параметрами, телами и ответами |
| `components` | Повторно используемые части: `schemas`, `responses`, `parameters`, `securitySchemes` |

### 11.3. Пример

```yaml
openapi: 3.0.3
info:
  title: Room Booking API
  version: 1.0.0
servers:
  - url: http://localhost:3000
paths:
  /rooms/{roomId}:
    get:
      operationId: getRoom
      summary: Получить аудиторию по идентификатору
      tags: [Rooms]
      parameters:
        - name: roomId
          in: path
          required: true
          schema:
            type: integer
            minimum: 1
      responses:
        '200':
          description: Аудитория найдена
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Room'
        '404':
          description: Аудитория не найдена
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
components:
  schemas:
    Room:
      type: object
      required: [id, name, capacity]
      additionalProperties: false
      properties:
        id:
          type: integer
          example: 1
        name:
          type: string
          example: A-101
        capacity:
          type: integer
          minimum: 1
          example: 30
    Error:
      type: object
      required: [code, message]
      properties:
        code:
          type: string
          example: NOT_FOUND
        message:
          type: string
```

### 11.4. Ключевые элементы

**Операция** (метод у пути) описывается так:

| Поле | Смысл |
|---|---|
| `operationId` | Уникальное имя операции (используется при генерации клиентов): `getRoom` |
| `summary` / `description` | Краткое и подробное описание |
| `tags` | Группа в документации |
| `parameters` | Параметры: `in: path` / `query` / `header` / `cookie` |
| `requestBody` | Тело запроса (для POST, PUT, PATCH) |
| `responses` | Возможные ответы по кодам (`'200'`, `'404'`, `default`) |
| `security` | Требования к аутентификации |

**Схема данных** (на основе JSON Schema):

| Ключевое слово | Смысл |
|---|---|
| `type` | `string`, `integer`, `number`, `boolean`, `array`, `object` |
| `required` | Список обязательных полей объекта |
| `properties` | Описание полей |
| `format` | Уточнение: `date-time`, `email`, `uuid`, `int64` |
| `enum` | Допустимые значения |
| `minimum`, `maximum`, `minLength`, `maxLength`, `pattern` | Ограничения |
| `nullable: true` | Значение может быть `null` (в 3.0) |
| `additionalProperties: false` | Запрет лишних полей |
| `items` | Схема элементов массива |
| `example` / `examples` | Примеры значений |

**Ссылки `$ref`** — способ не дублировать описание: `$ref: '#/components/schemas/Room'`. Работают для схем, ответов, параметров, тел запросов.

### 11.5. Что должно быть описано

Хороший контракт описывает **не только успешный** сценарий:

- все возможные коды ответов, включая ошибки (400, 401, 404, 409, 500);
- формат ошибки (единая схема `Error`);
- ограничения полей (длина, диапазоны, обязательность);
- примеры ответов (по ним строятся моки и документация);
- коды без тела (`204 No Content`) и заголовки (`Location` у `201`).

### 11.6. Коды ответа: напоминание

| Код | Когда |
|---|---|
| `200 OK` | Успешное получение/изменение |
| `201 Created` | Ресурс создан (+ заголовок `Location`) |
| `204 No Content` | Успех без тела (например, удаление) |
| `400 Bad Request` | Некорректный запрос, ошибка валидации |
| `401` / `403` | Не аутентифицирован / нет прав |
| `404 Not Found` | Ресурс не найден |
| `409 Conflict` | Конфликт состояния (например, дубликат) |
| `422 Unprocessable Entity` | Синтаксически верный, но семантически неверный запрос |
| `500` | Ошибка сервера |

## 12. Design-first и code-first

| | Design-first (контракт вперёд) | Code-first (код вперёд) |
|---|---|---|
| Порядок | Сначала пишем `openapi.yaml`, потом код | Сначала код, спецификация генерируется из аннотаций |
| Плюсы | Обсуждение до реализации; frontend начинает сразу (моки); контракт — источник правды | Быстро стартовать; спецификация не расходится с кодом (если генерируется) |
| Минусы | Нужно дисциплинированно синхронизировать с кодом | Контракт «случайный»: меняется вместе с кодом, потребители не в курсе |
| Когда | Публичные API, несколько команд, параллельная разработка | Внутренние API, прототипы |

В нашем курсе — **design-first**: контракт сначала согласуется, потом реализуется, а **автотесты проверяют, что реализация ему соответствует**. Это защита от расхождений при любом подходе.

```
Design-first:
  1. Обсуждаем с потребителями  →  2. Пишем openapi.yaml  →  3. Ревью контракта (PR)
  →  4. Параллельно: backend реализует, frontend использует мок  →  5. Контрактные тесты в CI
```

## 14. Моки на основе контракта

### 14.1. Что такое мок

**Мок-сервер (mock server)** — программа, имитирующая API: принимает запросы и отдаёт ответы, сформированные **по спецификации** (из примеров или генерируемые по схемам). Реальной бизнес-логики и базы данных в нём нет.

### 14.2. Зачем нужны моки

- **Параллельная разработка.** Frontend не ждёт backend: контракт согласован — мок поднимается за секунды.
- **Предсказуемые сценарии.** Можно воспроизвести редкие случаи: ошибка 404, 500, пустой список.
- **Тесты клиента.** Тестирование интерфейса без нестабильного сервера.
- **Демонстрации и прототипы.**
- **Ранняя проверка контракта:** если клиенту не хватает поля, это видно до написания backend.

### 14.3. Схема

```
Без мока:       Frontend ──► (ждёт) ──► Backend не готов ✖

С моком:        Frontend ──► Prism (мок по openapi.yaml)   ← можно работать сразу
                Backend  ──► реализует тот же openapi.yaml
                Интеграция: поменять адрес мока на адрес реального сервера
```

### 14.4. Prism

Запуск:

```bash
npx @stoplight/prism-cli mock openapi.yaml -p 4010
```

Полезные возможности (названия параметров сверяйте с документацией вашей версии):

| Возможность | Как |
|---|---|
| Ответы из `example`/`examples` | По умолчанию |
| Динамические данные по схеме | Флаг `-d` |
| Выбрать код ответа | Заголовок `Prefer: code=404` |
| Выбрать пример | Заголовок `Prefer: example=имя` |
| Проверка входящего запроса по контракту | Включена: невалидный запрос получает ошибку |
| Режим прокси (проверка реального сервера по контракту) | `prism proxy openapi.yaml http://localhost:3000` |

### 14.5. Ограничения мока

- Мок **не хранит состояние**: создали ресурс, а он не появился в списке.
- Мок не проверяет бизнес-правила.
- Ответ мока верен лишь настолько, насколько хороши примеры в контракте.
- Мок **не доказывает**, что настоящий сервер ведёт себя так же. Для этого — контрактные тесты.

## 15. Контрактное тестирование

### 15.1. Определение

**Контрактное тестирование** проверяет, что **стороны взаимодействия соблюдают договорённость** (контракт): провайдер (сервер) отвечает в согласованном формате, а консьюмер (клиент) использует только то, что контракт гарантирует.

Оно отвечает на вопрос: «Не сломается ли интеграция, если я выпущу эту версию?» — **без** поднятия всех сервисов целиком.

### 15.2. Где находится в пирамиде тестирования

```
          ▲  E2E (мало, медленно, хрупко)
         ╱ ╲
        ╱───╲  Контрактные и интеграционные (средне)
       ╱─────╲
      ╱───────╲  Unit-тесты (много, быстро)
     ╱─────────╲
```

Контрактные тесты быстрее E2E и надёжнее ловят расхождения интерфейсов, чем unit-тесты.

### 15.3. Виды

**1. Проверка ответов провайдера на соответствие спецификации (schema-based, provider-side).**
Тест вызывает настоящий API и проверяет: код ответа описан в контракте, тело соответствует схеме. **Это мы будем делать на практике** (`jest-openapi` + `supertest`).

```
Тест ──запрос──► Ваш сервер ──ответ──► Проверка по openapi.yaml ──► ✅ / ❌
```

**2. Property-based / генеративное тестирование по спецификации.**
Инструмент (например, **Schemathesis**) **сам придумывает** множество запросов по схеме, включая странные граничные значения, и проверяет, что сервер не падает и отвечает по контракту. Находит ошибки, о которых вы не подумали.

**3. Consumer-driven contract testing (Pact).**
Контракт формулируют **потребители**: «мне нужно, чтобы на запрос X приходил ответ вида Y». Потребитель записывает ожидания в файл-контракт (pact), провайдер прогоняет их у себя.

```
Consumer test ──► создаёт pact-файл ──► Pact Broker ──► Provider verification
 (клиент)                                               (сервер проверяет, что
                                                         выполняет ожидания)
```

Подходит для микросервисов, когда много потребителей и важно знать, **кого сломает изменение**.

### 15.4. Сравнение подходов

| Критерий | Schema-based (OpenAPI) | Генеративный (Schemathesis) | Consumer-driven (Pact) |
|---|---|---|---|
| Источник контракта | Спецификация провайдера | Спецификация провайдера | Ожидания потребителей |
| Что находит | Расхождения ответа со схемой | Падения и нарушения на неожиданных входах | Что именно потребитель использует |
| Усилия на настройку | Малые | Малые | Выше (нужны тесты на стороне потребителя, брокер) |
| Лучше для | Один сервис + несколько клиентов, публичный API | Поиск скрытых ошибок | Сеть микросервисов |

### 15.5. Что проверяет контрактный тест, а что нет

| Проверяет | Не проверяет |
|---|---|
| Что код ответа описан в контракте | Правильность бизнес-логики (верна ли сумма) |
| Что структура и типы тела соответствуют схеме | Производительность, нагрузку |
| Что обязательные поля присутствуют | Безопасность и права доступа (кроме описанных) |
| Что нет лишних полей (если `additionalProperties: false`) | Работу в связке со всеми внешними системами |

Контрактные тесты **дополняют**, а не заменяют unit- и интеграционные тесты.

### 15.6. Пример проверки в коде (подход практической работы)

```js
const request = require('supertest');
const jestOpenAPI = require('jest-openapi').default;

jestOpenAPI('openapi.yaml');          // загружаем контракт

test('GET /rooms соответствует контракту', async () => {
  const res = await request(app).get('/rooms');
  expect(res.status).toBe(200);
  expect(res).toSatisfyApiSpec();     // код, тип и тело — как в openapi.yaml
});
```

Одна строка `toSatisfyApiSpec()` проверяет: путь и метод есть в спецификации, код ответа описан, тело проходит JSON-схему.

## 16. Совместимость и версионирование API

### 16.1. Что можно менять безболезненно

| Изменение | Совместимо? |
|---|---|
| Добавить новый эндпоинт | ✅ Да |
| Добавить необязательный параметр запроса | ✅ Да |
| Добавить новое поле в ответ | ✅ Обычно да (если клиенты не запрещают лишние поля) |
| Удалить эндпоинт | ❌ **Нет** (breaking) |
| Переименовать или удалить поле ответа | ❌ **Нет** |
| Изменить тип поля (`int` → `string`) | ❌ **Нет** |
| Сделать необязательный параметр обязательным | ❌ **Нет** |
| Сузить допустимые значения запроса | ❌ **Нет** |
| Изменить код ответа/формат ошибки | ❌ **Нет** |
| Добавить значение в `enum` ответа | ⚠️ Может сломать клиентов с жёсткой проверкой |

**Breaking change** (несовместимое изменение) ломает существующих клиентов. Потребители API не обязаны обновляться одновременно с вами.

### 16.2. Версионирование

| Способ | Пример |
|---|---|
| В URL | `/v1/rooms`, `/v2/rooms` |
| В заголовке | `Accept: application/vnd.api+json; version=2` |
| В параметре | `/rooms?version=2` |

Поле `info.version` в OpenAPI отражает версию контракта; используйте **семантическое версионирование**: MAJOR при несовместимых изменениях, MINOR при добавлении возможностей, PATCH при исправлениях описания.

### 16.3. Как менять API безопасно

1. Добавить новое, **не удаляя** старое.
2. Пометить старое как устаревшее: `deprecated: true` в OpenAPI.
3. Предупредить потребителей и назначить срок.
4. Через период поддержки удалить старое в новой мажорной версии.

### 16.4. Автоматическая проверка совместимости

Инструменты вроде **oasdiff** сравнивают две версии спецификации и сообщают о breaking changes:

```bash
oasdiff breaking openapi-main.yaml openapi-pr.yaml
```

В CI это позволяет **блокировать PR**, который случайно ломает контракт.

## 17. Контракт в CI: общая картина

Дополним пайплайн из части I проверками контракта:

```
┌──────────┐  ┌───────────────────────┐  ┌────────────────────────────┐  ┌───────┐  ┌──────────────────┐
│ Checkout │─►│ Lint                  │─►│ Test                       │─►│ Build │─►│ Upload Artifact  │
│          │  │  • ESLint (код)       │  │  • Unit-тесты              │  │       │  │  • сборка        │
│          │  │  • Spectral (openapi) │  │  • Контрактные тесты       │  │ + docs│  │  • HTML-доки API │
└──────────┘  └───────────────────────┘  └────────────────────────────┘  └───────┘  └──────────────────┘
                                                  ▲
                                     (по необходимости) oasdiff: нет breaking changes
```

Что именно ловит каждый уровень:

| Проверка | Что ловит |
|---|---|
| **Spectral lint** спецификации | Ошибки в самом `openapi.yaml`: нет `operationId`, битая `$ref`, несоответствие примера схеме |
| **Контрактные тесты** | Сервер отвечает не так, как описано |
| **oasdiff** | Изменение контракта ломает потребителей |
| **Артефакт с документацией** | Свежая документация API доступна команде с каждой сборки |

Итог: изменить поведение API, не обновив контракт (и наоборот), **становится невозможно** — CI покажет красный статус, а merge будет заблокирован.

## 18. Типичные ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| `npm install` вместо `npm ci` в CI | Невоспроизводимые сборки | `npm ci` и закоммиченный lock-файл |
| Один гигантский job на всё | Долго, неясно, что упало | Разделить на lint / test / build |
| Тесты не входят в CI | Пайплайн «зелёный» бессмысленно | Тесты — обязательный шаг |
| Красный CI не блокирует merge | Проверка формальна | Обязательные проверки в защите ветки |
| Версии без фиксации (`latest`) | Внезапные поломки | Фиксировать версии Node, действий, зависимостей |
| Секрет в коде или логе | Утечка | Secrets, маскирование, минимум прав |
| Артефакт — вся папка с `node_modules` | Гигабайты, медленно | Выгружать только результат сборки |
| `openapi.yaml` «для галочки», не проверяется | Документация врёт | Spectral + контрактные тесты в CI |
| Описан только код 200 | Клиент не знает про ошибки | Описывать все коды ответов и формат ошибки |
| Нет `additionalProperties: false` на ключевых схемах | Контракт не замечает лишних полей | Решить осознанно и закрепить в схеме |
| Мок принимается за истину | Расхождение с настоящим сервером | Контрактные тесты на реальном сервере |
| Breaking change без версии | Падают клиенты | Совместимые изменения, `deprecated`, новая мажорная версия |

## 19. Итоги, вопросы, литература

### 19.1. Ключевые идеи

1. **CI** — частая интеграция + автоматическая сборка и проверка каждого изменения.
2. Типовой пайплайн: **Checkout → Setup → Install → Lint → Test → Build → Upload Artifact**; дешёвые проверки идут первыми.
3. В **GitHub Actions**: workflow → jobs → steps; запуск по событиям; `needs` задаёт порядок; каждый job — на чистом runner.
4. **Кэш** ускоряет, **артефакт** сохраняет результат; **секреты** хранятся отдельно; **матрица** прогоняет на нескольких средах.
5. **Merge блокируется** не самим красным CI, а правилом обязательных проверок.
6. **OpenAPI** — машиночитаемый контракт API; он же — источник документации, моков, клиентов и тестов.
7. **Design-first**: сначала контракт, потом реализация; frontend работает с **моком**.
8. **Контрактные тесты** проверяют, что сервер соответствует `openapi.yaml`; **Spectral** проверяет качество самой спецификации.
9. Несовместимые изменения API (**breaking changes**) нужно обнаруживать автоматически и вводить через версии.

### 19.3. Мини-задачи

**Задача 1.** Допишите недостающие строки, чтобы job `build` запускался только после успешных `lint` и `test`:

```yaml
build:
  ______: [lint, test]
  runs-on: ubuntu-latest
```
*(Ответ: `needs`.)*

**Задача 2.** Найдите ошибку: артефакт не появляется на странице запуска, шаг зелёный.

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: app
    path: build/
```
*(Ответ: сборка создаёт каталог `dist/`, а не `build/`; без `if-no-files-found: error` отсутствие файлов даёт лишь предупреждение. Нужно указать верный путь и включить `if-no-files-found: error`.)*

**Задача 3.** По фрагменту контракта определите, пройдёт ли ответ `{"id": "5", "name": "A-101", "capacity": 30}`:

```yaml
Room:
  type: object
  required: [id, name, capacity]
  properties:
    id: { type: integer }
    name: { type: string }
    capacity: { type: integer }
```
*(Ответ: не пройдёт: `id` — строка, а в контракте `integer`.)*

**Задача 4.** Какие из изменений ломают клиентов? а) добавили `GET /rooms/{id}/bookings`; б) поле `capacity` переименовали в `seats`; в) в ответ добавили необязательное поле `floor`; г) параметр `minCapacity` стал обязательным.
*(Ответ: б и г. Пункт в обычно совместим, а пункт а совместим.)*

**Задача 5.** Опишите в OpenAPI ответ `404` для операции получения ресурса, используя общую схему `Error` из `components`.
*(Подсказка: `responses` → `'404'` → `content` → `application/json` → `schema` → `$ref: '#/components/schemas/Error'`.)*
