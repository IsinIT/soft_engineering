## 2. Зачем автоматизировать проверку качества кода

В прошлой теме мы настроили локальные хуки. Они помогают, но их можно обойти (`--no-verify`) или не установить. Чтобы качество кода не зависело от дисциплины каждого, проверки переносят в **общий, обязательный для всех** этап — **CI**.

Что мы получаем:

1. **Единый стандарт.** Код выглядит одинаково независимо от автора.
2. **Раннюю обратную связь.** Ошибка находится за минуты, а не при ручном тестировании или в продакшене.
3. **Экономию времени ревьюеров.** Люди не спорят о пробелах и кавычках, а обсуждают логику и архитектуру.
4. **Снижение технического долга.** Проблемы не накапливаются.
5. **Обучение.** Правила линтера объясняют, почему так писать нельзя.

> **Принцип:** всё, что можно проверить машиной, должно проверяться машиной. Время человека — для того, что машина проверить не может.

Стоимость исправления ошибки растёт со временем. Чем раньше найдена проблема, тем дешевле её устранить:

```
Стоимость
исправления
   │                                         ╱ продакшен
   │                                   ╱╱╱╱╱
   │                           ╱╱╱╱╱╱╱╱  тестирование
   │                  ╱╱╱╱╱╱╱╱╱
   │        ╱╱╱╱╱╱╱╱╱╱  ревью / CI
   │ ╱╱╱╱╱╱╱  редактор / хуки
   └──────────────────────────────────────→ Когда найдена ошибка
```

## 3. Форматтер, линтер, статический анализатор: в чём разница

### 3.1. Определения

**Форматтер (formatter)** — автоматически приводит **внешний вид** кода к единому стилю: отступы, кавычки, переносы строк. Логику не меняет.
Примеры: Prettier, Black, `gofmt`, `google-java-format`.

**Линтер (linter)** — ищет в коде **подозрительные конструкции, нарушения правил и потенциальные ошибки**: неиспользуемые переменные, `==` вместо `===`, слишком сложные функции.
Примеры: ESLint, Pylint, Ruff, Checkstyle.

**Статический анализатор (static analyzer)** — глубже анализирует код **без его запуска**: поток данных, возможные null-разыменования, уязвимости, дублирование, сложность, «запахи кода». Часто включает и функции линтера.
Примеры: SonarQube, SpotBugs, PMD, CodeQL.

> «Статический» значит, что код **не выполняется**: анализируется только исходный текст. Анализ с выполнением программы называется **динамическим** (тесты, профилирование, fuzzing).

### 3.2. Сравнение

| Критерий | Форматтер | Линтер | Статический анализатор |
|---|---|---|---|
| Что проверяет | Внешний вид | Стиль и типичные ошибки | Ошибки, уязвимости, сложность, дублирование |
| Может исправить сам | Да, всегда | Часть правил (`--fix`) | Обычно нет (подсказывает) |
| Скорость | Очень быстрая | Быстрая | Медленнее |
| Где запускается | Редактор, хук, CI | Редактор, хук, CI | В основном CI, сервер |
| Результат | Изменённые файлы | Список замечаний | Отчёт, метрики, Quality Gate |

### 3.3. Что именно находят анализаторы

| Категория | Пример |
|---|---|
| **Bug** (ошибка) | Деление на возможный ноль, разыменование `null`, неверное сравнение |
| **Vulnerability** (уязвимость) | SQL-инъекция, жёстко прописанный пароль, небезопасная криптография |
| **Code Smell** («запах кода») | Слишком длинная функция, вложенность 6 уровней, магические числа |
| **Duplication** | Копипаста блоков кода |
| **Security Hotspot** | Место, требующее ручной проверки безопасности |
| **Complexity** | Цикломатическая и когнитивная сложность функций |

### 3.4. Цикломатическая сложность

**Цикломатическая сложность** — число независимых путей выполнения функции. Считается как «1 + количество ветвлений» (`if`, `for`, `while`, `case`, `&&`, `||`, `catch`).

```js
function price(user, qty) {     // 1 (базовый путь)
  if (qty <= 0) return 0;       // +1
  if (user.vip && qty > 10) {   // +1 (if) +1 (&&)
    return qty * 8;
  }
  return qty * 10;
}                               // итого: 4
```

Ориентиры: до 10 — хорошо, 10–20 — подозрительно, выше 20 — пора разбивать функцию. Чем выше сложность, тем больше тестов нужно и тем легче ошибиться.

**Когнитивная сложность** (термин SonarSource) — метрика, ближе к тому, насколько код трудно **читать человеку** (вложенные условия «весят» больше).

## 4. Инструменты по языкам

| Язык | Форматтер | Линтер | Статический анализатор |
|---|---|---|---|
| JavaScript / TypeScript | Prettier | **ESLint** | SonarQube, CodeQL |
| Python | Black, Ruff format | **Pylint**, Ruff, flake8, mypy (типы) | SonarQube, Bandit (безопасность), CodeQL |
| Java | google-java-format | **Checkstyle** (стиль) | **SpotBugs**, PMD, SonarQube |
| C# | `dotnet format` | Roslyn analyzers | SonarQube |
| Go | `gofmt` | `golangci-lint` | SonarQube |

### 4.1. ESLint (JavaScript / TypeScript)

Самый распространённый линтер для JS. Правила настраиваются в файле `eslint.config.js`.

Ключевые идеи:
- уровни правил: `off`, `warn`, `error`;
- наборы правил (`recommended`);
- флаг `--fix` исправляет часть проблем автоматически;
- флаг `--max-warnings 0` превращает любое предупреждение в ошибку (важно для CI).

### 4.2. Pylint (Python)

Проверяет стиль (PEP 8), ошибки и «запахи». Выставляет **оценку от 0 до 10**.

- Коды сообщений: `C` (convention), `R` (refactor), `W` (warning), `E` (error), `F` (fatal).
- Конфигурация — `.pylintrc` или секция `[tool.pylint]` в `pyproject.toml`.
- Флаг `--fail-under=N` завершает работу с ошибкой, если оценка ниже порога.

Современная альтернатива — **Ruff**: линтер и форматтер на Rust, работает на порядок быстрее.

### 4.3. Checkstyle (Java)

Проверяет соответствие **стилю оформления** Java-кода: имена, отступы, длина строк, Javadoc. Готовые конфигурации: Google Style и Sun Style. Подключается как плагин Maven или Gradle; нарушения могут ронять сборку (`failOnViolation`).

Для поиска **ошибок** (не стиля) в Java используют SpotBugs и PMD.

### 4.4. Как выбрать

1. Берите **стандартный** инструмент вашей экосистемы.
2. Начните с **рекомендуемого набора правил** (`recommended`), а не с самых строгих.
3. Форматтер + линтер — минимальный набор для любого проекта.
4. Статический анализатор уровня SonarQube — для проектов, где важны безопасность, поддерживаемость и метрики.

## 5. Конфигурация правил и борьба с шумом

### 5.1. Конфигурация лежит в репозитории

Файлы `eslint.config.js`, `.pylintrc`, `checkstyle.xml`, `sonar-project.properties` **хранятся в Git** вместе с кодом. Так правила одинаковы у всех и меняются через Pull Request (с обсуждением).

### 5.2. Что делать, когда правил слишком много

Если включить всё сразу на старом проекте, получите **тысячи замечаний**, и команда начнёт игнорировать отчёт. Рекомендации:

1. Начать с набора `recommended`.
2. Исправить критичное (`error`), остальное временно оставить как `warn`.
3. Для унаследованного кода использовать **Clean as You Code** (см. раздел 7): проверять строго только новый и изменённый код.
4. Постепенно ужесточать правила.

### 5.3. Подавление замечаний (suppression)

Иногда правило срабатывает ошибочно или нарушение оправдано. Тогда подавление допустимо, но **точечно и с объяснением**:

```js
// eslint-disable-next-line no-console -- намеренный вывод в CLI-утилите
console.log(report);
```

```python
value = compute()  # pylint: disable=invalid-name  # имя задано внешним API
```

**Плохая практика:** отключать правило для всего проекта «потому что мешает»; глобальные `eslint-disable` в начале файла без причины; подавлять уязвимости без обсуждения.

### 5.4. Ложные срабатывания

Статический анализ не идеален: возможны **false positives** (ложные тревоги) и **false negatives** (пропущенные проблемы). Поэтому результаты анализа — повод подумать, а не истина в последней инстанции. Но вывод «это ложное срабатывание» должен быть обоснованным.

## 6. SonarQube: платформа непрерывной проверки качества

### 6.1. Что это

**SonarQube** — платформа с веб-интерфейсом, которая анализирует исходный код (десятки языков), собирает метрики и показывает проблемы по категориям. Она хранит **историю** анализа проекта, поэтому видно, улучшается ли качество.

Варианты:

| Вариант | Особенности |
|---|---|
| **SonarQube Community Build** | Бесплатная версия для самостоятельной установки (например, в Docker) |
| **SonarQube Server** (платные редакции) | Расширенные возможности: анализ веток и PR, больше языков и т. д. |
| **SonarQube Cloud** (ранее SonarCloud) | Облачный сервис, не требует установки; для открытых проектов есть бесплатный план |

> Состав редакций и условия тарифов меняются; актуальные сведения смотрите на сайте SonarSource.

### 6.2. Как это работает

```
Разработчик ──push/PR──► GitHub ──► CI (GitHub Actions)
                                       │
                                       ▼
                               sonar-scanner / action
                          (анализирует код, собирает покрытие)
                                       │ отправляет отчёт
                                       ▼
                               Сервер SonarQube / Cloud
                          (считает метрики, применяет Quality Gate)
                                       │ статус «Passed / Failed»
                                       ▼
                          Статус-проверка в Pull Request ──► блок merge
```

Важное: **сканер** (scanner) запускается в CI и отправляет результаты, а **сервер** хранит их и вычисляет итог.

### 6.3. Основные метрики

| Метрика | Что показывает |
|---|---|
| **Reliability** (надёжность) | Количество и серьёзность багов, оценка A–E |
| **Security** (безопасность) | Уязвимости, оценка A–E |
| **Maintainability** (поддерживаемость) | «Запахи кода», технический долг, оценка A–E |
| **Coverage** (покрытие) | Доля кода, выполняемого тестами |
| **Duplications** | Процент дублированного кода |
| **Technical Debt** | Оценка времени на устранение проблем |

Оценки A–E: A — лучшая, E — худшая.

### 6.4. Файл конфигурации сканера

`sonar-project.properties` в корне репозитория:

```properties
sonar.projectKey=my-org_my-project
sonar.projectName=My Project
sonar.sources=src
sonar.tests=src
sonar.test.inclusions=**/*.test.js
sonar.exclusions=**/node_modules/**,**/coverage/**
sonar.javascript.lcov.reportPaths=coverage/lcov.info
```

Для Python вместо `lcov` указывают `sonar.python.coverage.reportPaths=coverage.xml`, для Java — путь к отчёту JaCoCo.

> Сам Sonar **не запускает тесты**. Покрытие тестами генерирует ваш тестовый фреймворк, а Sonar лишь читает файл отчёта.

## 7. Quality Gate и подход Clean as You Code

### 7.1. Quality Gate

**Quality Gate (контрольные ворота качества)** — набор **условий**, которым должен удовлетворять код. Результат: **Passed** (зелёный) или **Failed** (красный).

Пример условий для стандартного «Sonar way»: на **новом коде**
- нет новых багов и уязвимостей;
- все Security Hotspots проверены;
- покрытие нового кода не ниже заданного порога (в стандартном шаблоне — 80 %);
- дублирование нового кода не выше порога (в стандартном шаблоне — 3 %);
- поддерживаемость нового кода — оценка A.

> Пороги зависят от версии и настроек. В вашем проекте их можно изменить.

### 7.2. Clean as You Code

Идея SonarSource: **не пытаться вылечить весь старый код сразу, а следить, чтобы новый и изменённый код был чистым.**

```
Старый код (технический долг)     │   Новый код (после даты/версии)
        не блокирует              │   проверяется строго → Quality Gate
────────────────────────────────────┼─────────────────────────────────►
                                 «точка отсчёта»                      время
```

Преимущества:
- можно внедрять на давно живущем проекте без «аврала»;
- со временем долг сокращается сам, потому что каждый затронутый участок приводят в порядок;
- у разработчика понятная ответственность: «мой PR не ухудшает качество».

### 7.3. Что такое «зелёный» пайплайн

**Зелёный пайплайн** — все шаги CI завершились успешно. В нашем случае это минимум:

1. форматирование соответствует стандарту;
2. линтер не нашёл нарушений (или только допустимые);
3. тесты проходят;
4. Quality Gate — Passed.

## 8. Интеграция в CI и блокировка merge

### 8.1. Принцип работы

CI-система запускает команды. Если команда возвращает **ненулевой код выхода**, шаг считается упавшим, весь job — красным. Линтеры устроены так, чтобы при нарушениях возвращать ненулевой код.

```
npm run lint ──► нарушения найдены ──► exit code 1 ──► шаг красный ──► PR нельзя слить
                 нарушений нет      ──► exit code 0 ──► шаг зелёный
```

Но сам по себе красный CI **не запрещает** слить PR. Запрет создаётся настройкой **защиты ветки**: «проверка X обязательна».

### 8.2. Две части блокировки

| Часть | Что делает |
|---|---|
| 1. **CI-шаг** | Запускает линтер и «падает» при нарушениях |
| 2. **Branch protection / Ruleset** | Требует успешного статуса проверки перед слиянием |

Без второй части красный CI — только совет. Без первой — нечему блокировать.

### 8.3. Пример: GitHub Actions + ESLint + Prettier

```yaml
name: Quality

on:
  pull_request:
  push:
    branches: [main]

jobs:
  lint:
    name: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: ESLint
        run: npx eslint . --max-warnings 0
      - name: Prettier (check)
        run: npx prettier --check .
      - name: Tests with coverage
        run: npm test
```

Заметьте `--max-warnings 0`: без него предупреждения (`warn`) не роняют сборку.

### 8.4. Пример: Pylint с порогом

```yaml
      - run: pip install pylint
      - run: pylint src --fail-under=9.0
```

Для строгой проверки без оценок можно использовать `pylint src --fail-on=E,W` (падение при ошибках и предупреждениях выбранных категорий); точный набор флагов зависит от версии Pylint.

### 8.5. Пример: Checkstyle (Maven)

В `pom.xml` подключают `maven-checkstyle-plugin` и задают, что нарушения прерывают сборку; команда проверки:

```bash
mvn checkstyle:check
```

### 8.6. Пример: SonarQube / SonarQube Cloud в GitHub Actions

```yaml
  sonar:
    name: sonar
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # полная история нужна для определения нового кода
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test -- --experimental-test-coverage   # или команда вашего фреймворка для lcov
      - name: SonarQube scan
        uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}   # для SonarQube Cloud не требуется
      - name: Quality Gate
        uses: SonarSource/sonarqube-quality-gate-action@v1
        timeout-minutes: 5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

> Версии действий в примерах условные: сверяйтесь с их страницами в GitHub Marketplace. Для SonarQube Cloud есть отдельная настройка «Automatic Analysis» без сканера в CI, однако для передачи покрытия и жёсткого управления шагами используется CI-вариант.

**Секреты.** Токен `SONAR_TOKEN` — это пароль. Его нельзя записывать в код или лог: храните в **GitHub → Settings → Secrets and variables → Actions**.

### 8.7. Обязательные проверки в защите ветки

Настройка в GitHub: **Settings → Rules → Rulesets** (или **Branches**):

- Require a pull request before merging;
- Require status checks to pass → выбрать задания `lint`, `sonar` (или общий `checks`);
- Require branches to be up to date before merging;
- Block force pushes.

После этого кнопка **Merge** в PR недоступна, пока проверки красные.

### 8.8. Скорость и надёжность CI

- Кэшируйте зависимости (`cache: npm`, `cache: pip`).
- Запускайте независимые шаги параллельно (отдельные jobs).
- Быстрые проверки (форматирование, линтер) делайте **первыми**: если они падают, нет смысла ждать долгие шаги.
- Если шаг «моргает» (flaky), чините его, а не нажимайте Re-run: иначе команда перестаёт доверять CI.

## 9. Зелёный пайплайн: как к нему прийти

Типичный путь внедрения на существующем проекте:

```
1. Зафиксировать текущее состояние (запустить линтер, сохранить отчёт)
2. Автоформатирование всего проекта ОДНИМ отдельным коммитом (style: apply prettier)
3. Исправить автоисправимые замечания (eslint --fix)
4. Критичные ошибки — исправить
5. Остальное — понизить до warn / включить Clean as You Code
6. Включить CI-шаг → он зелёный
7. Сделать проверку обязательной (branch protection)
8. Постепенно ужесточать правила
```

Правила хорошего тона:

- **Массовое форматирование — отдельным коммитом** (иначе в diff функциональных изменений не разобрать). Такой коммит добавляют в `.git-blame-ignore-revs`, чтобы `git blame` не показывал его как «автора» каждой строки.
- Не включайте строгие правила **одновременно** с блокировкой слияния на проекте с тысячами замечаний: сначала приведите код в порядок.
- Договоритесь о политике подавления: кто и как может отключать правило.

## 10. Code Review: люди там, где автоматика бессильна

### 10.1. Что распределяем между машиной и человеком

| Проверяет автоматика | Проверяет человек |
|---|---|
| Форматирование, стиль | Правильность решения задачи |
| Типичные ошибки и «запахи» | Архитектура и дизайн |
| Известные уязвимости | Понятность и читаемость для людей |
| Проход тестов, покрытие | Осмысленность и полнота тестов |
| Дублирование | Краевые случаи и бизнес-логика |
| Формат сообщений коммитов | Названия, которые «говорят» |

### 10.2. Зачем нужно ревью (повторим и расширим)

1. **Поиск дефектов:** свежий взгляд замечает то, что автор «замылил».
2. **Распространение знаний:** команда знает, как устроены разные части системы.
3. **Единые практики:** обсуждаются и закрепляются договорённости.
4. **Обучение:** новичок учится у опытных, опытные — объясняя.
5. **Коллективное владение кодом:** нет «моего» и «чужого» модуля.

### 10.3. Как организовать ревью

| Параметр | Рекомендация |
|---|---|
| Размер PR | До ~200–400 строк; больше — снижается качество ревью |
| Время ревью за один заход | Не более 60 минут, затем перерыв |
| Скорость ответа | В течение рабочего дня |
| Автор перед запросом ревью | Прочитал свой diff, CI зелёный, описание заполнено |
| Ревьюер | Понимает контекст (описание, задача) |
| Решение | **Approve**, **Comment** или **Request changes** |

### 10.4. Порядок чтения PR

Эффективное ревью идёт «сверху вниз»:

1. **Описание и задача:** чего хотел автор?
2. **Тесты:** по ним проще понять ожидаемое поведение.
3. **Структура изменений:** какие файлы и модули затронуты, нет ли лишнего?
4. **Логика:** построчное чтение ключевых мест.
5. **Крайние случаи:** что будет с пустым вводом, ошибкой, большим объёмом?
6. **Итог:** общее впечатление, решение.

## 11. Чек-лист ревью

Чек-лист не заменяет мышление, но помогает ничего не пропустить. Пройдите его по уровням.

### 11.1. Назначение и корректность

- [ ] Код решает поставленную задачу и соответствует критериям приёмки
- [ ] Нет очевидных логических ошибок
- [ ] Обработаны краевые случаи: `null`/пустое значение, ноль, отрицательные числа, очень большие данные
- [ ] Ошибки обрабатываются осмысленно (не «проглатываются» молча)
- [ ] Нет гонок и проблем с состоянием (если применимо)

### 11.2. Читаемость и поддерживаемость

- [ ] Имена переменных, функций, классов понятны
- [ ] Функции короткие и делают одну вещь
- [ ] Нет дублирования, которое стоит вынести
- [ ] Нет «магических чисел» и непонятных констант
- [ ] Комментарии объясняют **почему**, а не **что** (код сам говорит «что»)
- [ ] Нет закомментированного кода и отладочных выводов

### 11.3. Архитектура и дизайн

- [ ] Код находится в подходящем месте (модуль, слой, пакет)
- [ ] Нет лишних зависимостей и «протекающих» абстракций
- [ ] Решение не сложнее, чем нужно (нет лишней «гибкости на вырост»)
- [ ] Публичные интерфейсы продуманы и стабильны

### 11.4. Тесты

- [ ] Есть тесты на новую логику
- [ ] Проверяются и обычный сценарий, и ошибки, и границы
- [ ] Тесты понятны и независимы друг от друга
- [ ] Тесты проверяют поведение, а не детали реализации

### 11.5. Безопасность

- [ ] Нет паролей, ключей, токенов в коде и истории
- [ ] Входные данные проверяются и очищаются
- [ ] Нет SQL-запросов, склеенных из пользовательского ввода
- [ ] Права доступа учитываются
- [ ] Зависимости не содержат известных уязвимостей (проверено инструментами)

### 11.6. Производительность

- [ ] Нет запросов к БД/сети в цикле
- [ ] Нет заведомо неэффективных алгоритмов на больших данных
- [ ] Ресурсы (файлы, соединения) освобождаются

### 11.7. Процесс и документация

- [ ] PR небольшой и сфокусирован на одной задаче
- [ ] Заголовок и описание понятны, есть ссылка на задачу
- [ ] README/документация обновлены, если поведение изменилось
- [ ] CI зелёный, Quality Gate пройден

## 12. Как писать комментарии: тактичная критика

Код ревьюят **люди**, и критика кода легко воспринимается как критика человека. Тон влияет на результат не меньше, чем содержание.

### 12.1. Принципы

1. **Критикуйте код, а не человека.** Не «ты написал плохо», а «эта функция сложна для чтения».
2. **Объясняйте почему.** «Переименуй» — слабый комментарий. «Имя `data` не говорит, что внутри; предлагаю `activeUsers`» — сильный.
3. **Предлагайте, а не приказывайте.** Вопросы и предложения вызывают диалог.
4. **Конкретика.** Ссылайтесь на строки, приводите пример.
5. **Различайте важность.** Блокирующее — отдельно от пожеланий.
6. **Отмечайте хорошее.** Похвала мотивирует и показывает, что нужно сохранить.
7. **Предполагайте добрые намерения.** Возможно, автор знает то, чего вы не знаете.
8. **Не обсуждайте то, что проверяет автоматика.** Стиль — задача линтера.

### 12.2. Метки важности

Простая система префиксов делает намерение ясным:

| Метка         | Значение                                             | Блокирует слияние? |
| ------------- | ---------------------------------------------------- | ------------------ |
| `blocker:`    | Ошибка или серьёзная проблема, исправить обязательно | **Да**             |
| `suggestion:` | Предложение по улучшению, обсудим                    | Нет, но желательно |
| `nit:`        | Мелочь (nitpick), на усмотрение автора               | Нет                |
| `question:`   | Мне непонятно, объясните                             | По ответу          |
| `praise:`     | Удачное решение                                      | Нет                |

### 12.3. Примеры: плохо и хорошо

| Плохо                          | Лучше                                                                                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| «Это ужасно, переделай»        | «`suggestion:` Функция `processOrder` делает три разных вещи (валидация, расчёт, сохранение). Может, разделим на три функции? Тогда будет проще тестировать» |
| «Почему ты не написал тесты?!» | «`blocker:` Для ветки с `qty <= 0` нет теста. Можешь добавить? Без него изменение сложно считать безопасным»                                                 |
| «Неправильное имя»             | «`nit:` Имя `tmp` можно заменить на `parsedDate`, так понятнее»                                                                                              |
| «Ты забыл проверку на null»    | «`question:` Что произойдёт, если `user` придёт как `null`? Кажется, на строке 42 будет исключение»                                                          |
| «Это не будет работать»        | «`blocker:` При `b = 0` получим деление на ноль (строка 17). Предлагаю добавить проверку и тест»                                                             |
| «LGTM» (без чтения)            | «`praise:` Хорошо, что вынесли парсинг в отдельную функцию. Я проверил краевые случаи, остальное выглядит корректным. Approve»                               |

### 12.4. Формулы, которые помогают

- «Я заметил… Может быть, стоит… Потому что…»
- «Что ты думаешь о варианте…?»
- «Не уверен, что понял. Объясни, пожалуйста, зачем здесь…»
- «Круто, что… Это сильно упростило…»
- «Это можно исправить в отдельном PR, если сейчас нет времени»

### 12.5. Чего избегать

- Сарказма, иронии, «шуток» над чужим кодом.
- Слов «очевидно», «просто», «любой знает».
- Обобщений вроде «ты всегда…» и «ты никогда…».
- Лавины комментариев по мелочам: отберите главное.
- Споров в комментариях: если не договорились за 2–3 реплики, обсудите голосом.

## 13. Как принимать критику (роль автора)

1. **Замечание — к коду, а не к вам.** Ревью — способ сделать продукт лучше.
2. **Благодарите** и отвечайте по существу.
3. **Не спорьте из принципа.** Если не согласны, приведите аргументы и факты.
4. **Задавайте вопросы,** если непонятно.
5. **Отмечайте, как исправлено:** «Сделано в коммите `abc123`».
6. **Закрывайте обсуждения** (Resolve) только после реального исправления или договорённости.
7. **Не вносите посторонние изменения** в PR на этапе ревью; мелкие улучшения «заодно» усложняют проверку.
8. **Перед запросом ревью** посмотрите на свой diff глазами ревьюера: часть замечаний вы найдёте сами.

## 14. Кросс-ревью между командами: как проходит сессия

**Кросс-ревью** — формат, в котором команды меняются репозиториями и проводят ревью чужого кода. Это ценно, потому что:

- вы читаете код **без знания контекста**, как это бывает при подключении к новому проекту;
- нет «слепоты автора»;
- вы учитесь формулировать критику людям, с которыми не сидите рядом;
- видите, как те же задачи решают другие.

### 14.1. Ход сессии

```
1. Команды обмениваются ссылками на репозитории (или ветки)
        ↓
2. Знакомство: README, структура, запуск проекта (10–15 мин)
        ↓
3. Ревью по чек-листу: читаем код, запускаем, проверяем CI (40–50 мин)
        ↓
4. Комментарии в Pull Request: метки blocker/suggestion/nit/question/praise
        ↓
5. Решение: Approve / Request changes + итоговый комментарий
        ↓
6. Команда-автор отвечает на замечания и вносит правки (20–30 мин)
        ↓
7. Повторное ревью и закрытие обсуждений
        ↓
8. Обсуждение в аудитории: что узнали, какая критика была самой полезной
```

### 14.2. Роли

| Роль | Задача |
|---|---|
| **Ревьюеры** | Изучают код, оставляют комментарии, принимают решение |
| **Авторы** | Отвечают на комментарии, исправляют, благодарят |
| **Фасилитатор** (преподаватель) | Следит за тоном, помогает при спорах, разбирает примеры |

### 14.3. Правила игры

1. Только конструктивная критика с метками важности.
2. Минимум **8 содержательных комментариев** на репозиторий, в том числе минимум **1 `praise`**, **2 `question`**, **минимум 1 `blocker`** (если в коде нет блокирующих проблем, сформулируйте самую значимую как `blocker` с обоснованием, либо объясните в итоге, почему ни одной нет).
3. Не «чинить» чужой код самим: ревьюер предлагает, автор исправляет.
4. Оценка зависит от **качества ревью**, а не от «количества найденных ошибок».

## 15. Типичные ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| CI красный, но merge разрешён | Проверка превращается в формальность | Сделать проверку обязательной в защите ветки |
| Линтер только локально | Обход, у части разработчиков не установлен | Дублировать в CI |
| Включить все правила сразу | Тысячи замечаний, их игнорируют | `recommended`, постепенно ужесточать, Clean as You Code |
| Глобальные отключения правил | Теряется смысл проверки | Точечные подавления с комментарием |
| Токен Sonar в коде | Утечка секрета | GitHub Secrets |
| Массовое форматирование вместе с функциональными правками | Нечитаемый diff | Отдельный коммит |
| Покрытие ради цифры | Тесты без проверок | Смотреть на осмысленность тестов |
| Ревью «LGTM» без чтения | Баги проходят | Чек-лист, минимум один содержательный комментарий |
| Обсуждение стиля на ревью | Тратится время людей | Автоматизировать форматтером и линтером |
| Резкий тон комментариев | Конфликты, страх ревью | Метки важности, вопросы, похвала |
| Огромный PR | Ревью поверхностное | Разбивать на небольшие |

## 16. Итоги, вопросы, литература

### 16.1. Ключевые идеи

1. **Форматтер** меняет внешний вид, **линтер** находит подозрительные конструкции, **статический анализатор** ищет глубокие проблемы без запуска кода.
2. Конфигурация правил живёт в репозитории и меняется через PR.
3. **SonarQube** собирает метрики и применяет **Quality Gate** к новому коду (подход **Clean as You Code**).
4. Блокировка слияния = **CI-шаг, который падает** + **обязательная проверка в защите ветки**.
5. **Зелёный пайплайн** — форматирование, линтер, тесты и Quality Gate пройдены.
6. Всё, что может проверить машина, проверяет машина; **люди проверяют смысл, дизайн и тесты**.
7. Хорошее ревью — это чек-лист, метки важности, вопросы и похвала; хороший автор — спокойный и благодарный.

### 16.2. Вопросы для самопроверки

1. Чем форматтер отличается от линтера и от статического анализатора? Приведите по примеру.
2. Что значит «статический» анализ?
3. Что такое цикломатическая сложность? Посчитайте её для функции с тремя `if` и одним `for`.
4. Почему красный CI сам по себе не блокирует слияние? Что для этого нужно?
5. Зачем `--max-warnings 0` в ESLint и `--fail-under` в Pylint?
6. Что такое Quality Gate? Из каких условий он может состоять?
7. В чём суть подхода Clean as You Code?
8. Почему токен SonarQube нужно хранить в Secrets?
9. Что такое ложное срабатывание? Как правильно подавлять замечание?
10. Что в Code Review оставляют человеку, а что автоматике?
11. Для чего нужны метки `blocker`, `suggestion`, `nit`, `question`?
12. Переформулируйте комментарий «Тупой код, перепиши» тактично.

### 16.3. Мини-задачи

**Задача 1.** Посчитайте цикломатическую сложность:

```js
function check(a, b) {
  if (a > 0 && b > 0) {
    for (let i = 0; i < a; i++) {
      if (i % 2 === 0) { b += i; }
    }
  }
  return b;
}
```

*(Ответ: 1 + `if` (1) + `&&` (1) + `for` (1) + внутренний `if` (1) = 5.)*

**Задача 2.** Команда включила ESLint в CI, но разработчик всё равно слил PR с красным CI. Назовите причину и решение.
*(Ответ: проверка не отмечена как обязательная в защите ветки (Branch protection/Ruleset). Добавить её в Required status checks и запретить обход.)*

**Задача 3.** Улучшите комментарий ревьюера: «Здесь всё неправильно, нет проверок».
*(Пример ответа: «`blocker:` В функции `save` (строка 25) нет проверки на пустой `name`: при пустом значении мы запишем некорректную запись в БД. Предлагаю добавить валидацию и тест на этот случай. Что думаешь?»)*

**Задача 4.** Проект на Python, оценка Pylint — 6,5. Команда хочет внедрить обязательную проверку. Предложите план.
*(Пример: зафиксировать текущую оценку, автоформатировать (Black/Ruff), исправить `E`/`W`, поставить `--fail-under=6.5`, затем поднимать порог по шагам; сделать шаг обязательным.)*
