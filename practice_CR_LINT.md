## 1. Цель и результаты

**Цель:** настроить автоматическую и обязательную проверку качества кода в CI, добиться «зелёного» пайплайна, а затем приобрести опыт чтения чужого кода и тактичной критики на кросс-ревью.

**После выполнения работы вы:**

- настроите CI-шаги ESLint и Prettier, которые падают при нарушениях;
- подключите статический анализатор (SonarQube / SonarQube Cloud) и настроите Quality Gate;
- сделаете проверки **обязательными** для слияния в `main`;
- пройдёте путь от «красного» к «зелёному» пайплайну;
- проведёте полноценное Code Review чужого репозитория по чек-листу;
- научитесь писать комментарии с метками важности и отвечать на критику.

**Итоговые артефакты:**

| Артефакт | Где |
|---|---|
| Зелёный пайплайн качества (lint + format + тесты + Sonar) | вкладка Actions |
| Файлы конфигурации | `eslint.config.js`, `sonar-project.properties`, `.github/workflows/quality.yml` |
| Обязательные проверки в защите `main` | Settings → Rules |
| Ревью чужого PR (≥ 8 комментариев, итоговое решение) | Pull Request соседней команды |
| Ответы на ревью своего PR, доработки | Pull Request вашей команды |
| Отчёт | `docs/report.md` |

## Шаг 1. Красный пайплайн: воспроизводим проблему

Прежде чем чинить, увидим, что значит «красный» CI и почему он пока ничего не блокирует.

### 1.1. Ветка и «грязный» код

```bash
git switch main && git pull
git switch -c feat/orders-module
```

Создайте файл `src/orders.js` с **намеренно плохим** кодом (хуки Husky отработают при коммите, поэтому для демонстрации используем `--no-verify` на этой учебной ветке; в реальной работе так делать нельзя):

```js
// src/orders.js
var TAX = 0.2

export function calcTotal(items, discount) {
  var total = 0
  for (var i = 0; i < items.length; i++) {
    if (items[i].price == null) {
      console.log("no price for", items[i].name)
    } else {
      total = total + items[i].price * items[i].qty
    }
  }
  if (discount != undefined) {
    total = total - total * discount
  }
  return total + total * TAX
}

export function unusedHelper(x) {
  return x
}
```

Тест `src/orders.test.js`:

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { calcTotal } from './orders.js';

test('calcTotal: сумма без скидки', () => {
  assert.equal(calcTotal([{ name: 'a', price: 100, qty: 1 }]), 120);
});
```

```bash
git add src/orders.js src/orders.test.js
git commit --no-verify -m "feat(orders): add calcTotal"
git push -u origin feat/orders-module
```

### 1.2. Откройте Pull Request и посмотрите на CI

На GitHub создайте PR. На вкладке **Checks** вы должны увидеть красный результат: ESLint ругается (`no-var`, `eqeqeq`), Prettier — на форматирование.

### 1.3. Проверьте, блокируется ли merge

Если в настройках `main` из прошлой работы **обязательной проверкой** указан `checks`, кнопка Merge заблокирована. Если же в вашем репозитории обязательных проверок нет, кнопка активна, **несмотря на красный CI**.

**Зафиксируйте в отчёте:**
- скриншот красного CI с перечнем ошибок;
- состояние кнопки Merge;
- ваш вывод: что именно делает проверку «блокирующей» (подсказка: CI-шаг + требование статуса в защите ветки).

> **Ветку не закрывайте** — мы доведём её до зелёного состояния.

## Шаг 2. Усиление ESLint и CI-шаг линтера

### 2.1. Ужесточите правила

Откройте `eslint.config.js` и дополните правила (сохраните существующие):

```js
rules: {
  eqeqeq: 'error',
  'no-var': 'error',
  'prefer-const': 'error',
  'no-console': 'warn',
  'no-unused-vars': 'error',
  complexity: ['error', 8],
  'max-lines-per-function': ['warn', { max: 40, skipBlankLines: true, skipComments: true }],
  'max-depth': ['warn', 3],
  'no-magic-numbers': ['warn', { ignore: [0, 1, -1, 2], ignoreArrayIndexes: true }],
  curly: ['error', 'all'],
},
```

Что означают новые правила:

| Правило | Смысл |
|---|---|
| `no-unused-vars` | Запрет неиспользуемых переменных и функций |
| `complexity` | Цикломатическая сложность функции не выше 8 |
| `max-lines-per-function` | Функция не длиннее 40 строк |
| `max-depth` | Вложенность блоков не глубже 3 |
| `no-magic-numbers` | «Магические числа» должны быть вынесены в константы |
| `curly` | Фигурные скобки обязательны в `if`/`for` |

### 2.2. Запустите локально

```bash
npx eslint . --max-warnings 0
```

Убедитесь, что **предупреждения (warn)** тоже считаются ошибкой благодаря `--max-warnings 0`. Обратите внимание, что без этого флага код выхода был бы `0` даже при предупреждениях:

```bash
npx eslint . ; echo "exit code: $?"
npx eslint . --max-warnings 0 ; echo "exit code: $?"
```

📝 **В отчёт:** выводы обеих команд и коды выхода.

### 2.3. Обновите скрипты

В `package.json`:

```json
"scripts": {
  "lint": "eslint . --max-warnings 0",
  "format:check": "prettier --check .",
  "test": "node --test",
  "test:coverage": "node --test --experimental-test-coverage --test-reporter=lcov --test-reporter-destination=coverage/lcov.info --test-reporter=spec --test-reporter-destination=stdout"
}
```

> Если ваша версия Node.js не поддерживает эти флаги, используйте `c8`: `npm i -D c8` и скрипт `"test:coverage": "c8 --reporter=lcov --reporter=text node --test"`. Это стабильный вариант, он создаёт `coverage/lcov.info`.

### 2.4. Отдельный workflow качества

Создайте `.github/workflows/quality.yml`:

```yaml
name: Quality

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: quality-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    name: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: ESLint (warnings are errors)
        run: npm run lint
      - name: Prettier check
        run: npm run format:check

  test:
    name: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test
```

Пояснения:
- два независимых job: `lint` и `test` выполняются **параллельно**;
- `concurrency` отменяет устаревшие запуски при новых коммитах в ту же ветку;
- имена `lint` и `test` понадобятся в Шаге 6.

> Если в репозитории остался старый `ci.yml`, он дублирует эти проверки. Удалите дубли, чтобы не получать двойную нагрузку: оставьте единый набор workflow, а в защите ветки обновите список обязательных проверок (Шаг 6).

```bash
git add .
git commit -m "ci: add lint and test jobs, tighten eslint rules"
git push
```

(Новые файлы конфигурации пройдут через хуки. Если Prettier переформатирует файлы, добавьте их снова.)

**Проверьте:** на вкладке Actions в PR видны задания `lint` и `test`; `lint` красный (код в `orders.js` ещё плохой), `test` зелёный.

## Шаг 4. Подключение SonarQube

Выберите **один** из вариантов. **Вариант 1 (рекомендуется)** не требует установки.

### Вариант 1. SonarQube Cloud (облако)

1. Откройте https://sonarcloud.io (сервис работает под названием SonarQube Cloud) и войдите через **GitHub**.
2. Нажмите **«+» → Analyze new project** (или **Import an organization**).
3. Выберите организацию/аккаунт GitHub и разрешите доступ к репозиторию `tbd-hooks-lab`.
4. Выберите метод анализа **With GitHub Actions** (CI-based). Если сервис предлагает «Automatic Analysis», отключите его для этого проекта, так как нам нужно передавать покрытие из CI.
5. Сервис покажет:
   - **Project key** и **Organization key** (запишите);
   - инструкцию по созданию секрета `SONAR_TOKEN`.
6. Создайте токен: **My Account → Security → Generate Tokens**, имя `ci-token`, скопируйте значение (показывается один раз).
7. В GitHub: **Settings → Secrets and variables → Actions → New repository secret**:
   - Name: `SONAR_TOKEN`
   - Secret: вставьте токен.

>  **Токен — это пароль.** Не вставляйте его в код, в issue, в скриншоты отчёта. Если токен утёк — отзовите и создайте новый.

### Вариант 2. SonarQube Community Build в Docker (локально)

1. Запустите сервер:

```bash
docker run -d --name sonarqube -p 9000:9000 sonarqube:community
```

2. Подождите 1–2 минуты и откройте http://localhost:9000. Логин и пароль по умолчанию — `admin` / `admin`; система потребует сменить пароль.
3. **Create a project → Manually**: имя и ключ `tbd-hooks-lab`, Main branch `main`.
4. Создайте токен: **My Account → Security → Generate Tokens**.
5. Локальный запуск сканера (без CI):

```bash
npm install --save-dev @sonar/scan
npx @sonar/scan -Dsonar.host.url=http://localhost:9000 -Dsonar.token=<ВАШ_ТОКЕН>
```

> **Ограничение варианта 2:** GitHub Actions в облаке не видит ваш `localhost`. Для интеграции с CI нужен общедоступный сервер Sonar (его предоставит преподаватель) либо вариант 1. Анализ веток и Pull Request в Community Build ограничен; детали зависят от версии, смотрите документацию.

### 4.1. Конфигурация сканера

Создайте `sonar-project.properties` в корне:

```properties
# Для SonarQube Cloud укажите свои значения:
sonar.organization=<ваша_организация>
sonar.projectKey=<ваш_ключ_проекта>

sonar.projectName=tbd-hooks-lab
sonar.sources=src
sonar.tests=src
sonar.test.inclusions=**/*.test.js
sonar.exclusions=**/node_modules/**,coverage/**
sonar.javascript.lcov.reportPaths=coverage/lcov.info
sonar.sourceEncoding=UTF-8
```

(Строку `sonar.organization` для локального сервера Community Build уберите.)

**Проверьте:** проект создан на стороне Sonar; секрет `SONAR_TOKEN` добавлен; файл `sonar-project.properties` готов.

## Шаг 5. Sonar в CI и Quality Gate

### 5.1. Добавьте job `sonar`

В `.github/workflows/quality.yml` добавьте в `jobs:`:

```yaml
  sonar:
    name: sonar
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # нужна полная история для определения нового кода
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - name: Tests with coverage
        run: npm run test:coverage
      - name: SonarQube scan
        uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          # SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}   # только для собственного сервера
      - name: Quality Gate check
        uses: SonarSource/sonarqube-quality-gate-action@v1
        timeout-minutes: 5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          # SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
```

Разъяснение:
- **scan** отправляет результаты анализа и покрытие на сервер;
- **Quality Gate check** ждёт вердикта и **падает**, если Gate = Failed. Именно это превращает Sonar в блокирующую проверку.

> **Ограничение для форков.** Секреты не передаются в workflow для PR из **форков**. Для кросс-ревью по ветке в одном репозитории проблем нет. Если используете форки, учитывайте, что Sonar-шаг для них не получит токен и будет пропущен или упадёт.

```bash
git add .
git commit -m "ci: add sonarqube scan and quality gate"
git push
```

### 5.2. Изучите отчёт Sonar

Откройте проект на сайте Sonar. Найдите:

- вкладку **Issues** (Bugs, Vulnerabilities, Code Smells);
- вкладку **Security Hotspots**;
- метрики **Coverage**, **Duplications**, **Maintainability rating**;
- статус **Quality Gate** (Passed/Failed) и условия, из-за которых он не пройден.

**В отчёт:**
- скриншот обзора проекта в Sonar;
- таблица: 3–5 найденных проблем с категорией (Bug/Smell/Vulnerability), серьёзностью и вашим вердиктом (исправить / подавить с обоснованием / ложное срабатывание).

### 5.3. Настройте Quality Gate (по желанию)

**Quality Gates → Create** (в облаке функция может быть ограничена тарифом): создайте Gate `Strict` для нового кода:

| Условие | Порог |
|---|---|
| Coverage on New Code | ≥ 80 % |
| Duplicated Lines on New Code | ≤ 3 % |
| Maintainability Rating on New Code | A |
| Reliability Rating on New Code | A |
| Security Rating on New Code | A |
| Security Hotspots Reviewed | 100 % |

Назначьте его своему проекту. Если создание Gate недоступно, работайте с вариантом по умолчанию **Sonar way** и просто опишите его условия в отчёте.

**Проверьте:** в PR появился job `sonar`; он красный, потому что Quality Gate не пройден; в логе виден вердикт.

## Шаг 6. Блокировка merge

Теперь делаем проверки обязательными.

### 6.1. Обновите правило защиты `main`

**Settings → Rules → Rulesets** (или **Branches → Branch protection rule** для `main`):

| Параметр | Значение |
|---|---|
| Require a pull request before merging | ✅ |
| Require status checks to pass | ✅ |
| &nbsp;&nbsp;Required checks | **`lint`**, **`test`**, **`sonar`** |
| Require branches to be up to date before merging | ✅ |
| Require conversation resolution before merging | ✅ |
| Block force pushes | ✅ |
| Do not allow bypassing the above settings (если есть) | ✅ |

> Названия проверок в выпадающем списке появляются **после первого запуска** workflow. Если нужной проверки нет, дождитесь завершения запуска и воспользуйтесь поиском. Если в списке остались старые проверки (например, `checks` из прошлой работы), которых больше нет, удалите их из обязательных: иначе PR будет «ждать» несуществующую проверку.

### 6.2. Проверьте блокировку

Откройте ваш PR `feat/orders-module`. Должно быть так:

- в нижней части: **«Required statuses must pass before merging»**;
- проверки `lint`, `sonar` — красные ✖;
- кнопка **Merge** неактивна.

**В отчёт:** скриншот заблокированной кнопки Merge и списка обязательных проверок. **Это ключевое доказательство выполнения задания «блокировка merge».**

## Шаг 7. Из красного в зелёное

Теперь исправим код так, чтобы все проверки прошли. **Важно:** исправлять нужно *причины*, а не подавлять правила.

### 7.1. Автоисправление

```bash
npx eslint . --fix
npx prettier --write .
git diff
```

Изучите, что изменилось автоматически (`var` → `const`/`let`, кавычки, `;`).

### 7.2. Ручное исправление

Оставшиеся замечания исправьте вручную. Ориентир по улучшению `src/orders.js`:

```js
const TAX_RATE = 0.2;

function isValidItem(item) {
  return Number.isFinite(item.price) && Number.isInteger(item.qty) && item.qty > 0;
}

export function calcSubtotal(items) {
  return items.filter(isValidItem).reduce((sum, item) => sum + item.price * item.qty, 0);
}

export function applyDiscount(amount, discount = 0) {
  if (discount < 0 || discount > 1) {
    throw new RangeError('Discount must be between 0 and 1');
  }
  return amount * (1 - discount);
}

export function calcTotal(items, discount = 0) {
  const discounted = applyDiscount(calcSubtotal(items), discount);
  return discounted * (1 + TAX_RATE);
}
```

Что улучшено: константа вместо «магического числа», нет `var` и `==`, нет `console.log`, удалён неиспользуемый код, функции маленькие, добавлена валидация скидки.

### 7.3. Тесты для покрытия

Дополните `src/orders.test.js` так, чтобы покрыть новую логику и ошибки:

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { calcSubtotal, applyDiscount, calcTotal } from './orders.js';

test('calcSubtotal: суммирует корректные позиции', () => {
  const items = [
    { name: 'a', price: 100, qty: 2 },
    { name: 'b', price: 50, qty: 1 },
  ];
  assert.equal(calcSubtotal(items), 250);
});

test('calcSubtotal: игнорирует позиции без цены или с нулевым количеством', () => {
  const items = [
    { name: 'a', price: null, qty: 1 },
    { name: 'b', price: 10, qty: 0 },
  ];
  assert.equal(calcSubtotal(items), 0);
});

test('applyDiscount: применяет скидку', () => {
  assert.equal(applyDiscount(200, 0.25), 150);
});

test('applyDiscount: ошибка при некорректной скидке', () => {
  assert.throws(() => applyDiscount(100, 1.5), RangeError);
  assert.throws(() => applyDiscount(100, -0.1), RangeError);
});

test('calcTotal: итог с налогом', () => {
  assert.equal(calcTotal([{ name: 'a', price: 100, qty: 1 }]), 120);
});

test('calcTotal: итог со скидкой и налогом', () => {
  assert.equal(calcTotal([{ name: 'a', price: 100, qty: 1 }], 0.5), 60);
});
```

```bash

npm run format:check
npm test
npm run test:coverage
```

Теперь коммит **без** `--no-verify` (хуки должны пройти):

```bash

```

### 7.5. Дождитесь зелёного

В PR на вкладке Checks: `lint`, `test`, `sonar`. Если `sonar` остаётся красным, откройте отчёт: Quality Gate указывает, какое условие не выполнено (покрытие нового кода, дублирование, уязвимость). Исправьте и повторите.

### 7.6. Слияние

Нужен approve напарника (по правилам защиты). После одобрения — **Squash and merge**, заголовок по Conventional Commits.

**Проверьте:** PR слит, на `main` пайплайн Quality зелёный.

**В отчёт:**
- скриншот зелёных проверок в PR;
- скриншот Quality Gate = Passed;
- сравнение «до/после»: количество замечаний ESLint, оценки Sonar, покрытие;

## Альтернативы: Pylint и Checkstyle

Если ваш проект на Python или Java, выполните эквивалентные шаги 2–6.

### Python (Pylint + Black/Ruff + pytest)

`pyproject.toml` (фрагмент):

```toml
[tool.pylint.main]
max-line-length = 100
fail-under = 9.0

[tool.pylint.messages_control]
disable = ["missing-module-docstring"]

[tool.pytest.ini_options]
addopts = "--cov=src --cov-report=xml"
```

Workflow:

```yaml
jobs:
  lint:
    name: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - run: pip install pylint black pytest pytest-cov
      - run: black --check .
      - run: pylint src
  test:
    name: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - run: pip install pytest pytest-cov
      - run: pytest
```

Для Sonar: `sonar.python.coverage.reportPaths=coverage.xml`, `sonar.sources=src`.

Особенность Pylint: он выставляет **оценку** из 10. Порог задаётся `fail-under`. Ужесточайте порог постепенно.

### Java (Checkstyle + SpotBugs + JUnit/JaCoCo)

В `pom.xml` подключите `maven-checkstyle-plugin` (с `failsOnError`/`failOnViolation`) и, по желанию, `spotbugs-maven-plugin`, `jacoco-maven-plugin`. Команды в CI:

```yaml
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: maven
      - run: mvn -B checkstyle:check
      - run: mvn -B verify          # тесты + JaCoCo
```

Для Sonar: `sonar.java.binaries=target/classes`, `sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml`.

> Для обоих вариантов обязательны: (1) CI-шаг, который **падает**; (2) обязательная проверка в защите `main`; (3) подтверждение в отчёте — скриншот красного и затем зелёного пайплайна.

## Часть Б. Кросс-ревью

**Идея:** команды меняются репозиториями и проводят настоящее Code Review. Ваш код прочитает незнакомый человек. Вы тоже прочитаете чужой. Цель — научиться читать чужой код и критиковать тактично.

## Шаг 8. Подготовка кода к ревью

Каждая команда готовит **небольшой Pull Request** для ревью: 100–300 строк изменений в одной ветке, решающий одну осмысленную задачу.

### 8.1. Выберите задачу

Подойдёт любая из следующих:

| №   | Задача                                                      | Идея                                   |
| --- | ----------------------------------------------------------- | -------------------------------------- |
| 1   | Модуль «Список дел»: добавление, удаление, фильтрация задач | Работа с массивами, валидация          |
| 2   | Модуль «Склад»: приход/расход товара, проверка остатков     | Правила предметной области             |
| 3   | Валидация паролей и e-mail                                  | Регулярные выражения, граничные случаи |
| 4   | Парсер CSV-строки в объекты                                 | Обработка ошибок, пустые значения      |
| 5   | Корзина интернет-магазина с промокодами                     | Расчёты, скидки                        |
|     |                                                             |                                        |

### 8.2. Требования к подготовке

1. Ветка от актуального `main`: `feat/<краткое-название>`.
2. Минимум 3–4 функции/класса, тесты на основную логику.
3. **Все локальные хуки пройдены, CI может быть зелёным**: ревью нужно не для поиска стиля.
4. Описание PR заполнено по шаблону (что, зачем, как проверить, чек-лист автора).
5. PR **не сливается**: он ждёт ревью.

> **Для честного ревью:** автор не должен «закладывать» ошибки специально. Пишите так, как пишете обычно. (Если преподаватель хочет проверить умение находить дефекты, он выдаст команды с заранее подготовленным кодом: см. Приложение Д.)

### 8.3. Откройте доступ

В **Settings → Collaborators** добавьте участников команды-ревьюера (права **Write**) или попросите их оставлять комментарии как внешних участников (для публичных репозиториев комментировать PR может любой пользователь GitHub; одобрять в рамках правил защиты — только участники с доступом).

Передайте напарникам ссылку на ваш PR.

**Проверьте:** PR открыт, описание заполнено, CI запущен, ссылка передана команде-ревьюеру.

## Шаг 10. Проведение ревью по чек-листу

Время: **40–50 минут**. Работайте по порядку чтения из лекции: описание → тесты → структура → логика → крайние случаи.

### 10.1. Чек-лист ревьюера

Скопируйте в итоговый комментарий ревью и отмечайте по мере проверки:

## Чек-лист ревью

**Назначение и корректность**
- [ ] Код решает заявленную задачу
- [ ] Нет очевидных логических ошибок
- [ ] Обработаны краевые случаи (пустое значение, ноль, отрицательные, очень большие данные)
- [ ] Ошибки обрабатываются осмысленно

**Читаемость**
- [ ] Имена понятны
- [ ] Функции короткие, одна ответственность
- [ ] Нет дублирования и «магических чисел»
- [ ] Комментарии объясняют «почему», а не «что»

**Архитектура**
- [ ] Код лежит в подходящем месте
- [ ] Нет лишней сложности
- [ ] Публичный интерфейс продуман

**Тесты**
- [ ] Есть тесты на основную логику
- [ ] Покрыты ошибки и границы
- [ ] Тесты читаемы и независимы

**Безопасность**
- [ ] Нет секретов в коде
- [ ] Ввод проверяется
- [ ] Нет небезопасных конструкций

**Процесс**
- [ ] PR небольшой, описание ясное
- [ ] CI зелёный
- [ ] Документация обновлена

### 10.2. Как оставлять комментарии

**К строке кода:** вкладка **Files changed** → наведите курсор на номер строки → «+» → напишите комментарий → **Start a review** (комментарии копятся и отправляются пачкой, а не по одному).

**Предложение правки:** внутри комментария нажмите значок **±** (Insert a suggestion) — GitHub покажет блок «suggestion», который автор сможет применить одним щелчком. Используйте для мелких правок (опечатки, имена).

**Общий комментарий:** в итоговом ревью (шаг 11).

### 10.3. Метки важности

Каждый комментарий начинайте с метки:

| Метка | Когда использовать | Блокирует? |
|---|---|---|
| `blocker:` | Ошибка/риск, без исправления слияние недопустимо | Да |
| `suggestion:` | Предложение по улучшению | Нет |
| `nit:` | Мелочь | Нет |
| `question:` | Нужны пояснения | По ответу |
| `praise:` | Удачное решение | Нет |

### 10.4. Минимальные требования к ревью

- **не менее 8 содержательных комментариев** (не считая «ок», «+1», «LGTM»);
- минимум **1 `praise`**;
- минимум **2 `question`**;
- минимум **1 `blocker`** (если в коде нет блокирующих проблем, найдите самую значимую и обоснуйте её важность, либо объясните в итоговом комментарии, почему блокеров нет);
- минимум **1 `suggestion` с блоком suggestion** (кнопка ±);
- хотя бы **2 комментария** про тесты или краевые случаи;
- ни один комментарий не обсуждает то, что проверяет линтер/форматтер (если CI зелёный).

### 10.5. Тактичность: самопроверка перед отправкой

Перед нажатием **Finish your review** перечитайте каждый комментарий:

- [ ] Критикует **код**, а не человека?
- [ ] Объясняет **почему**?
- [ ] Предлагает **конкретное** решение или задаёт вопрос?
- [ ] Нет сарказма и слов «очевидно», «просто», «всегда», «никогда»?
- [ ] Метка соответствует важности?

**Примеры преобразований:**

| Черновик | После правки |
|---|---|
| «Функция огромная» | «`suggestion:` `processCart` (строки 12–74) делает проверку, расчёт и форматирование. Разделение на три функции упростит тесты. Как думаешь?» |
| «Нет проверки ввода» | «`blocker:` `addTask(title)` принимает пустую строку (строка 21) — в списке появится «пустая» задача. Предлагаю проверить `title.trim()` и вернуть ошибку; добавить тест» |
| «Название плохое» | «`nit:` `x` → `taskCount`: так читается лучше» |
| «Мне не понятно» | «`question:` Зачем здесь `setTimeout` (строка 40)? Если это обход проблемы, может, добавим комментарий?» |

### 10.6. Что делать, если код очень хороший

Это нормально. Тогда:
- отмечайте удачные решения (`praise:`);
- ищите пробелы в тестах и краевых случаях (`question:`);
- предлагайте улучшения читаемости и документации (`suggestion:`/`nit:`);
- проверьте, не усложнено ли решение больше необходимого.

Не придумывайте проблемы искусственно: ложные замечания тоже хуже тишины.

## Шаг 12. Ответы автора и доработка

Время: **20–30 минут**. Команда-автор получает ревью своего PR.

### 12.1. Прочитайте ревью спокойно

1. Сначала прочитайте итоговый комментарий.
2. Разберите комментарии по меткам: сначала `blocker`, затем `question`, затем `suggestion`, затем `nit`.
3. Если эмоции мешают, сделайте паузу. Критика кода — не критика вас.

### 12.2. Отвечайте на каждый комментарий

Для каждого обсуждения выберите одно из:

| Ситуация | Действие |
|---|---|
| Согласны | «Спасибо, поправил в `abc1234`» → **Resolve** |
| Не согласны | Вежливо объясните аргументы и факты, предложите альтернативу, оставьте обсуждение открытым |
| Нужен ответ на вопрос | Ответьте и при необходимости добавьте пояснение в код (комментарий) или описание |
| Хорошее предложение, но не сейчас | «Принято, вынесу в отдельный Issue #N» → создайте Issue |
| Мелочь `nit:` | Исправьте или объясните, почему оставляете |

### 12.3. Внесите исправления

```bash
git switch feat/<ваша-ветка>
# правки...
git add .
git commit -m "fix(<область>): address review comments"
git push
```

> Для удобства ревьюера делайте исправления **отдельными коммитами** во время ревью (не переписывайте историю `force push`-ом): так видно, что изменилось. Объединит всё squash при слиянии.

Дождитесь зелёного CI.

### 12.4. Запросите повторное ревью

В правой панели PR нажмите значок **Re-request review** у ревьюера (⟳). Ревьюер проверяет исправления, закрывает обсуждения и меняет решение на **Approve**, если всё в порядке.

### 12.5. Слияние

После одобрения и зелёных проверок — **Squash and merge**.

**В отчёт:**
- таблица «комментарий → реакция автора → результат» (минимум 5 строк);
- ссылка на PR после исправлений;
- что вы изменили в коде по результатам ревью.

## Содержание отчёта

Оформляется в Markdown (`docs/report.md` в репозитории) или PDF.

1. **Титульная информация:** ФИО, группа, команда, роли, дата.
2. **Ссылки:** репозиторий, проект в Sonar, PR из части А, ревью, которое вы провели (часть Б), ваш PR, прошедший ревью.
3. **Часть А:**
   4. Красный пайплайн и состояние кнопки Merge (шаг 1).
   5. Конфигурация ESLint и вывод запусков с кодами выхода (шаг 2).
   6. Отчёт о покрытии (шаг 3).
   7. Конфигурации `quality.yml` и `sonar-project.properties`, описание подключения Sonar (шаги 4–5).
   8. Анализ проблем Sonar (таблица, шаг 5.2).
   9. Настройки обязательных проверок и скриншот заблокированного Merge (шаг 6).
   10. Результат «до/после» и скриншоты зелёного пайплайна (шаг 7).
11. **Часть Б:**
   12. Описание вашего PR для ревью.
   13. Заметки о знакомстве с чужим репозиторием (шаг 9).
   14. Заполненный чек-лист и ссылки на 3 самых важных комментария (шаги 10–11).
   15. Таблица «комментарий → реакция → результат» (шаг 12).
   16. Рефлексия (шаг 13).
17. **Выводы:** что даёт блокирующий CI, что — ревью; какие метрики и правила вы бы оставили в реальном проекте.

## Критерии оценивания

### Часть А (50 баллов)

| Критерий | Баллы |
|---|---|
| ESLint (или Pylint/Checkstyle) настроен, правила осмысленные, CI-шаг падает при нарушениях (доказано красным запуском) | 10 |
| Форматтер в CI (`prettier --check` / `black --check`) | 4 |
| Отчёт о покрытии формируется и передаётся в Sonar | 6 |
| SonarQube подключён, анализ запускается из CI, секреты хранятся корректно | 10 |
| Quality Gate-проверка в CI; анализ найденных проблем в отчёте | 6 |
| Обязательные проверки в защите `main`; подтверждена блокировка merge | 8 |
| Пайплайн зелёный; исправления по существу, без необоснованных подавлений | 6 |

### Часть Б (50 баллов)

| Критерий | Баллы |
|---|---|
| Подготовленный PR: небольшой, осмысленный, заполненное описание, чек-лист автора | 6 |
| Качество ревью: ≥ 8 содержательных комментариев, требуемые типы меток, блок suggestion | 14 |
| Глубина: найдены проблемы логики/тестов/краевых случаев, а не только стиль | 8 |
| Тактичность формулировок (объяснения, вопросы, предложения, похвала) | 8 |
| Итоговый комментарий и чек-лист ревью, корректное решение (Approve/Request changes) | 4 |
| Работа автора с ревью: ответы, исправления, Resolve, повторный запрос | 6 |
| Рефлексия | 4 |

**Итого: 100 баллов.**

**Шкала:** 85–100 — «отлично»; 70–84 — «хорошо»; 50–69 — «удовлетворительно»; менее 50 — «не зачтено».

> **Штрафы:** токен в коде/скриншотах — −10; необоснованное подавление правил (`eslint-disable`, «False Positive» без объяснения) — до −5; грубый или обидный комментарий в ревью — до −10 и обязательный разбор на занятии.

## Приложения

### Приложение А. Итоговый workflow `quality.yml` (ориентир)

```yaml
name: Quality

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: quality-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    name: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run format:check

  test:
    name: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm test

  sonar:
    name: sonar
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run test:coverage
      - uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
      - uses: SonarSource/sonarqube-quality-gate-action@v1
        timeout-minutes: 5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

### Приложение Б. Частые проблемы и решения

| Проблема | Возможная причина | Решение |
|---|---|---|
| `lint` зелёный, хотя есть warn | Нет `--max-warnings 0` | Добавить флаг в скрипт `lint` |
| В списке обязательных проверок нет `sonar` | Workflow ещё не запускался | Запустить на PR, подождать 1–2 минуты |
| PR «ждёт» проверку, которая не приходит | Обязательной указана несуществующая проверка (старое имя) | Удалить из обязательных, добавить актуальные |
| Sonar: «Not authorized» / 401 | Неверный или отсутствующий `SONAR_TOKEN` | Проверить секрет; создать новый токен |
| Sonar: «Project not found» | Неверные `projectKey` / `organization` | Сверить значения с сайтом Sonar |
| Sonar: покрытие 0 % | Не найден `lcov.info` или неверный путь | Проверить `sonar.javascript.lcov.reportPaths`, наличие файла после теста |
| Sonar Quality Gate всегда «Failed» из-за старого кода | Старый долг | Использовать оценку на **новом коде** (Clean as You Code), проверить New Code period |
| Sonar-шаг падает в PR из форка | Секреты недоступны форкам | Использовать ветки в одном репозитории |
| Quality Gate action ждёт слишком долго | Сервер перегружен | Увеличить `timeout-minutes` или повторить запуск |
| `npm ci` падает | `package-lock.json` не совпадает с `package.json` | Выполнить `npm install`, закоммитить lock-файл |
| Хуки Husky меняют файлы, но PR красный на `format:check` | Файлы не добавлены после автоформатирования | `git add` и повторный коммит; запускать `npx prettier --write .` |
| Комментарий в PR «не отправляется» | Использовались одиночные комментарии, но не завершён review | Нажать **Finish your review → Submit review** |
| Нельзя одобрить собственный PR | Автор не может сам одобрить PR | Ревью выполняет другой участник |

### Приложение В. Шаблон комментариев ревью

```markdown

nit: <мелочь>.

```
