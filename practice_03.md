## 1. Цель и результаты

**Цель:** получить практические навыки оценки задач, ведения бэклога, планирования спринтов и релизов, а также расчёта метрик команды с помощью GitHub Projects.

**После выполнения работы вы:**

- создадите проект в GitHub Projects и настроите поля (Status, Estimate, Priority, Iteration и др.);
- оформите требования как User Story в виде Issues;
- проведёте Planning Poker и зафиксируете оценки в Story Points;
- спланируете и проведёте учебный спринт;
- оформите релиз с тегом и Release Notes;
- рассчитаете Velocity, Lead Time, Cycle Time и построите прогноз.

**Итоговый артефакт:** ссылка на репозиторий и проект GitHub + отчёт в формате Markdown/PDF.

---

## 2. Подготовка

**Что нужно:**

- аккаунт на GitHub у каждого участника;
- браузер, доступ в интернет;
- (желательно) установленный Git;
- колода карт Planning Poker (бумажная) или договорённость голосовать комментариями.

**Распределите роли в команде** (роли учебные, участвуют в работе все):

| Роль | Задачи |
|---|---|
| **Product Owner (PO)** | Ведёт бэклог, расставляет приоритеты, принимает работу |
| **Scrum Master (SM)** | Следит за процессом, ведёт встречи, фиксирует метрики |
| **Разработчики** (1–2 человека) | Оценивают и выполняют задачи |

Запишите состав команды и роли в отчёт.

## 3. Легенда проекта

Ваша команда разрабатывает продукт **«Сервис бронирования аудиторий»** для университета. Студенты и преподаватели смотрят свободные аудитории и бронируют их на нужное время.

> Вы можете **заменить тему** на свою (например, свой курсовой проект) — по согласованию с преподавателем. Тогда сформируйте бэклог аналогичного размера.

**Допущения для учебного режима:**

- спринт длится **1 неделя** (условно — в занятии мы его «сожмём»; даты в проекте заполняем так, как будто спринт идёт по календарю);
- реальная разработка продукта в рамках занятия не требуется: «выполнением» задачи считается небольшой **проверяемый результат** (файл с документом, макет, заготовка кода, тест).

## Шаг 1. Репозиторий и метки

### 1.1. Создайте репозиторий

1. Перейдите на https://github.com и нажмите **«+» → New repository**.
2. Укажите имя, например, `room-booking`.
3. Тип — **Public** (или Private, добавив преподавателя как Collaborator).
4. Отметьте **Add a README file**.
5. Нажмите **Create repository**.

### 1.2. Пригласите команду

1. Откройте **Settings → Collaborators** (или **Collaborators and teams**).
2. Нажмите **Add people** и добавьте всех участников и преподавателя.
3. Каждый принимает приглашение (приходит на e-mail или в уведомления GitHub).

### 1.3. Создайте метки (Labels)

1. Откройте вкладку **Issues → Labels**.
2. Нажмите **New label** и создайте метки:

| Метка | Назначение | Пример цвета |
|---|---|---|
| `feature` | Новая функция | зелёный |
| `bug` | Ошибка | красный |
| `tech-task` | Техническая задача | серый |
| `docs` | Документация | синий |
| `epic` | Крупная тема | фиолетовый |

> Некоторые метки (`bug`, `documentation`) уже есть по умолчанию — можно использовать их.

 **Проверьте:** в репозитории есть все участники и набор меток.

## Шаг 2. Шаблон User Story

Чтобы все Issues были оформлены единообразно, создайте шаблон.

1. В репозитории нажмите **Add file → Create new file**.
2. В поле имени введите путь: `.github/ISSUE_TEMPLATE/user-story.md` (слэши создадут папки автоматически).
3. Вставьте содержимое:

```markdown
---
name: User Story
about: Пользовательская история
title: "[US] "
labels: feature
---

## История
Как **<роль>**, я хочу **<действие>**, чтобы **<ценность>**.

## Критерии приёмки
- [ ] Дано ..., когда ..., тогда ...
- [ ] Дано ..., когда ..., тогда ...

## Definition of Done
- [ ] Результат оформлен через Pull Request
- [ ] Минимум одно ревью
- [ ] Критерии приёмки проверены
- [ ] Документация обновлена (если нужно)

## Заметки
(зависимости, ссылки, макеты)
```

4. Нажмите **Commit changes** → закоммитьте в ветку `main`.

 **Проверьте:** при создании нового Issue (**Issues → New issue**) появляется выбор шаблона «User Story».

## Шаг 3. Создание проекта и полей

### 3.1. Создайте проект

1. Откройте вкладку **Projects** репозитория (или профиля) → **New project**.
2. Выберите шаблон **Table** (или **Board**, или **Blank**). Название — `Room Booking Planning`.
3. Нажмите **Create project**.

### 3.2. Подключите репозиторий

1. В проекте нажмите **⋯ (меню) → Settings**.
2. В разделе **Manage access** при необходимости добавьте участников (Collaborators).
3. Откройте вкладку **Projects** в репозитории → **Link a project** и выберите ваш проект, чтобы Issues из репозитория легко добавлялись.

### 3.3. Настройте поле Status

1. В таблице проекта нажмите на заголовок колонки **Status → Edit field** (или **⋯ → Settings → Status**).
2. Создайте значения (порядок важен):

| Значение | Смысл |
|---|---|
| `Backlog` | Идея в бэклоге, ещё не готова к работе |
| `Ready` | Готова к взятию в спринт (выполнен DoR) |
| `In progress` | В работе |
| `In review` | На проверке |
| `Done` | Завершено по DoD |

### 3.4. Добавьте остальные поля

В таблице проекта нажмите **«+»** справа от заголовков колонок → **New field** и создайте:

| Поле | Тип | Значения / настройка |
|---|---|---|
| `Estimate` | **Number** | Story Points |
| `Priority` | **Single select** | `P0 – Must`, `P1 – Should`, `P2 – Could` |
| `Iteration` | **Iteration** | Длительность — 1 неделя, дата начала — понедельник текущей недели; добавьте не менее 4 итераций |
| `Started` | **Date** | Дата начала работы (для Cycle Time) |
| `Finished` | **Date** | Дата завершения (для Cycle Time) |
| `Release` | **Single select** | `v0.1.0`, `v0.2.0`, `Later` |

> **Зачем поля `Started`/`Finished`?** GitHub автоматически хранит дату **создания** и **закрытия** Issue (этого достаточно для Lead Time), но момент **начала работы** нужно фиксировать самим для расчёта Cycle Time.

### 3.5. Включите встроенную автоматизацию

1. В проекте нажмите **⋯ → Workflows**.
2. Включите (Enable) и настройте:
   - **Item added to project** → Set `Status` = `Backlog`;
   - **Item closed** → Set `Status` = `Done`;
   - **Pull request merged** → Set `Status` = `Done`;
   - **Auto-add to project** (если доступно) — для автоматического добавления новых Issues репозитория.
3. Нажмите **Save and turn on workflow** для каждого.

**Проверьте:** в проекте видны поля Status, Estimate, Priority, Iteration, Started, Finished, Release; автоматизации включены.

Product Owner совместно с командой создаёт Issues по шаблону User Story. Ниже — **стартовый список** для темы из легенды (допустимо дополнить своими пунктами; **минимум 14 историй**):

### 4.2. Создайте Issue — по шагам

1. Откройте **Issues → New issue → User Story → Get started**.
2. Заполните заголовок, историю и критерии приёмки (минимум 2 критерия).
3. Справа проверьте **Labels** (например, `feature`).
4. В поле **Projects** выберите ваш проект.
5. Нажмите **Submit new issue**.

> Повторите для каждой истории. Распределите создание между участниками: так быстрее.

### 4.3. Добавьте эпики (необязательно)

Создайте Issue `[EPIC] Бронирование аудиторий` с меткой `epic` и перечислите в нём ссылки на связанные Issues в виде списка задач:

```markdown
- [ ] #5
- [ ] #6
- [ ] #7
```

GitHub отобразит прогресс выполнения списка.

**Проверьте:** во вкладке Issues не менее 14 историй, все добавлены в проект со статусом `Backlog`.

**В отчёт:** скриншот таблицы проекта с бэклогом.

## Шаг 5. Оценка: Planning Poker

### 5.1. Подготовка

- Выберите **эталонную историю**. Рекомендуется «Войти и выйти из системы» (#2) = **3 SP**; можно выбрать иную, главное — согласовать в команде. Запишите выбор в отчёте.
- Договоритесь о шкале: **1, 2, 3, 5, 8, 13, 20, ?, ☕**.
- Product Owner **не голосует**, но отвечает на вопросы.

### 5.2. Проведение сессии

Для каждой истории (по очереди, в порядке бэклога):

1. PO зачитывает историю и критерии приёмки.
2. Команда задаёт уточняющие вопросы (5 минут максимум).
3. Каждый разработчик выбирает карту и кладёт лицом вниз.
4. По команде SM («Три, два, один — открываем!») все открывают карты.
5. Если оценки совпали — фиксируем.
6. Если нет — **минимум и максимум** объясняют свои аргументы (по 1 минуте), затем голосуем снова (до 3 раундов).
7. Если консенсуса нет — берём **наибольшую** оценку и записываем сомнения в комментарий.

> **Онлайн-вариант.** Если нет карт: каждый пишет свою оценку в личном сообщении фасилитатору, и тот объявляет все числа одновременно. Либо используйте любой бесплатный онлайн-инструмент Planning Poker.

### 5.3. Зафиксируйте результаты

1. В Issue добавьте **комментарий** о том, как проходили раунды, например:
   `Раунд 1: 3 / 5 / 8. Раунд 2: 5 / 5 / 5. Итог: 5 SP. Риск: нужна интеграция с почтовым сервисом.`
2. В проекте в колонке **Estimate** введите итоговое число.
3. Если история получила **13 и больше** — разбейте её на несколько мелких Issues, закройте исходную как `Duplicate`/`Not planned` со ссылкой на новые и оцените новые.
4. Если история получила «?» — добавьте комментарий с вопросом к PO и пометьте историю статусом `Backlog` (не `Ready`).

### 5.4. Заполните таблицу оценок (для отчёта)

| № Issue | Название | Раунд 1 | Раунд 2 | Итог (SP) | Комментарий |
|---|---|---|---|---|---|
| #2 | Вход и выход | 3 / 3 / 3 | — | 3 | Эталон |
| #5 | Бронирование | 8 / 5 / 13 | 8 / 8 / 8 | 8 | Нужна проверка пересечений |
| … | … | … | … | … | … |

> Образец строки — не обязательные значения; ваши оценки будут своими.

**Проверьте:** у всех историй заполнено поле Estimate (кроме отложенных с «?»), нет историй больше 8–13 SP без разбиения.

 **В отчёт:** таблица оценок + скриншот проекта с заполненной колонкой Estimate.

## Шаг 6. Приоритизация и настройка представлений

### 6.1. Расставьте приоритеты

1. PO определяет приоритет каждой истории по методу **MoSCoW**:
   - `P0 – Must` — без этого MVP не имеет смысла (например: регистрация, вход, список аудиторий, бронирование, защита от пересечений);
   - `P1 – Should` — важно (отмена, мои брони, уведомления);
   - `P2 – Could` — желательно (отчёт в PDF, регулярные брони).
2. Заполните колонку **Priority** в таблице.
3. Упорядочьте таблицу: перетащите строки так, чтобы **верх бэклога** содержал самые приоритетные элементы. (Если порядок не сохраняется — убедитесь, что не включена сортировка по другой колонке: **⋯ у представления → Sort → No sorting**.)

### 6.2. Определите, что входит в MVP и релиз

1. Для `Must`-историй в поле **Release** выберите `v0.1.0`.
2. Для `Should` — `v0.2.0`.
3. Остальным — `Later`.

### 6.3. Создайте представления (Views)

В проекте над таблицей нажмите **«+ New view»** и создайте:

**Представление 1 — «Backlog» (Table)**

- Layout: **Table**.
- Фильтр (в строке фильтра сверху): `-status:Done`.
- Колонки: Title, Labels, Status, Priority, Estimate, Release, Iteration.
- Сортировка по порядку (вручную).
- **Group by → Release**, чтобы видеть состав релиза.
- Включите **Field sum → Estimate** (в меню представления **⋯ → Field sum** выберите `Estimate`) — над группами появится сумма SP.

**Представление 2 — «Sprint Board» (Board)**

- Layout: **Board**.
- Фильтр: `iteration:@current`.
- **Column by → Status**.
- Включите отображение `Estimate` на карточках (в **⋯ → Fields**).
- В **⋯ у колонки In progress → Set limit** (если доступно) задайте WIP-лимит, например, `3`. Если опция недоступна, договоритесь о лимите письменно в Working Agreement.

**Представление 3 — «Roadmap»**

- Layout: **Roadmap**.
- Включите отображение по **Iteration** (в настройках Roadmap выберите **Date fields → Iteration**), чтобы видеть историю по спринтам.

**Проверьте:** три представления настроены; в Backlog видны суммы SP по релизам.

**В отчёт:** скриншоты представлений «Backlog» и «Roadmap»; запишите, **сколько SP** запланировано в `v0.1.0`.

## Шаг 7. Планирование спринта 1

### 7.1. Определите ёмкость

Так как Velocity у новой команды ещё не известна, используем **ёмкость на основе доступных дней** (принцип «вчерашней погоды» подойдёт позднее).

Правило для учебной работы: **1 человек ≈ 3–5 SP за недельный спринт** (с поправкой на вашу шкалу SP). Пример: команда из 4 человек → ёмкость ≈ **12–16 SP**.

Запишите в отчёт: сколько людей, сколько доступно, итоговая ёмкость.

### 7.2. Сформулируйте цель спринта (Sprint Goal)

Одно предложение, например:

> «К концу спринта пользователь может зарегистрироваться, войти и увидеть список аудиторий».

### 7.3. Отберите истории в спринт

1. Откройте представление **Backlog**.
2. Берите истории **сверху вниз**, пока сумма SP не приблизится к ёмкости, но не превысит её.
3. Для каждой отобранной истории:
   - поле **Iteration** = `Iteration 1` (текущая);
   - **Status** = `Ready`.
4. Убедитесь, что для каждой истории выполнен **Definition of Ready**: есть критерии приёмки, оценка, понятно, что делать.

### 7.4. Разбейте истории на задачи

Для каждой истории из спринта создайте подзадачи — одним из способов:

- **список задач** (чек-лист) в теле Issue:
  ```markdown
  - [ ] Продумать схему данных
  - [ ] Реализовать форму
  - [ ] Написать тесты
  ```
- или создайте отдельные Issues и привяжите их через **Sub-issues** (если функция доступна в вашем интерфейсе).

### 7.5. Зафиксируйте Sprint Goal в проекте

Создайте Issue `Sprint 1 Goal` (метка `docs`), укажите цель, перечень историй, ёмкость и итоговое «обязательство» (сумма SP). Назначьте этот Issue на `Iteration 1`. Закрепите его (**Pin issue**) для видимости.

### 7.6. Назначьте исполнителей

Каждый разработчик выбирает себе историю (поле **Assignees**). Один исполнитель — одна история (в учебном режиме).

**Проверьте:** в `Iteration 1` суммарно не более ёмкости; у каждой истории есть исполнитель; Sprint Goal зафиксирован.

**В отчёт:** скриншот Sprint Board до начала работы; сумма SP, взятая в спринт.

## Шаг 8. Выполнение спринта

В учебном режиме мы **моделируем** неделю работы за 40–60 минут. Работайте по правилам настоящего Scrum.

### 8.1. Что считать «выполнением» истории

Так как цель — освоить процесс, а не писать весь сервис, договоритесь с преподавателем, что для каждой истории достаточно **небольшого проверяемого результата**. Примеры:

| История | Допустимый результат |
|---|---|
| Регистрация | Файл `docs/registration.md` с описанием API/формы и макетом |
| Список аудиторий | Заготовка кода или JSON-файл с тестовыми данными |
| Бронирование | Диаграмма последовательности или заготовка функции + тест |
| README | Заполненный README |
| CI | Файл `.github/workflows/ci.yml` |

Результат оформляется **через Pull Request** (см. ниже).

### 8.2. Рабочий процесс по задаче

Для каждой истории исполнитель делает следующее:

**1. Берёт задачу в работу**
- В проекте (Sprint Board) переносит карточку `Ready → In progress`.
- Заполняет поле **Started** = дата начала.

**2. Создаёт ветку**

Из Issue: справа в блоке **Development → Create a branch**; либо в терминале:

```bash
git checkout -b feature/5-booking
```

**3. Делает работу и коммиты**

```bash
git add .
git commit -m "Add booking draft (#5)"
git push -u origin feature/5-booking
```

**4. Открывает Pull Request**
- Нажимает **Compare & pull request**.
- В описании пишет: `Closes #5` — при слиянии Issue закроется автоматически.
- Добавляет ревьюера из команды.
- Переносит карточку в `In review`.

**5. Ревью и слияние**
- Ревьюер проверяет результат по критериям приёмки и DoD, оставляет комментарии или нажимает **Approve**.
- Автор нажимает **Merge pull request**.
- Issue закрывается, статус становится `Done` (благодаря автоматизации).
- Заполняется поле **Finished** = дата завершения.

### 8.3. Ежедневный скрам (Daily Scrum)

Проведите 2–3 коротких «ежедневных» встречи (по 3–5 минут), имитируя дни спринта. Каждый отвечает:

1. Что я сделал с прошлой встречи?
2. Что буду делать дальше?
3. Что мне мешает?

Результаты фиксируйте одной строкой в комментарии к Issue `Sprint 1 Goal`.

### 8.4. Правила спринта

- **WIP-лимит:** не более 3 карточек в `In progress`.
- Не добавляйте новые истории в спринт без согласия PO. Если добавили — отметьте в отчёте.
- Если история не завершена к концу спринта — она **не** засчитывается в Velocity и возвращается в бэклог (`Iteration` очистить или перенести на следующий).
- Каждый переход в статусы **обязательно** сопровождается заполнением дат `Started` / `Finished`.

### 8.5. Как «растянуть» даты (для расчёта метрик)

Поскольку реальный спринт — неделя, а у вас — 1–2 часа, в датах **Started** и **Finished** допускается проставлять **условные даты**, соответствующие дням «недели»: например, 1-й час — понедельник, 2-й — вторник и т. д. Преподаватель сообщит принятую в группе схему. (Даты **Created** и **Closed** у Issue останутся реальными — для Lead Time используйте условные даты из таблицы, которую дополнительно составите.)

> Для расчёта метрик в шаге 11 вам будут выданы данные «прошлых спринтов» — используйте их совместно с вашими.

**Проверьте:** карточки двигались по колонкам; у закрытых Issues заполнены **Started** и **Finished**; Pull Requests слиты.

**В отчёт:** скриншоты Sprint Board в начале и в конце; список PR (ссылки).

## Шаг 9. Ревью и ретроспектива спринта

### 9.1. Sprint Review (10 минут)

1. Команда демонстрирует (экран/ссылки) результаты завершённых историй.
2. PO проверяет **критерии приёмки** и принимает или отклоняет истории.
3. Отклонённые истории возвращаются в `In progress` или в бэклог.
4. Фиксируем: **запланировано** SP, **завершено** SP.

### 9.2. Sprint Retrospective (10 минут)

Создайте Issue `Retro Sprint 1` (метка `docs`) с содержанием:

```markdown
## Что получилось хорошо
- ...

## Что можно улучшить
- ...

## Действия на следующий спринт (не более 2-3, конкретно)
- [ ] ... (ответственный)
```

Например: «Проводить ревью PR в течение дня», «Разбивать истории > 5 SP».

### 9.3. Обновите бэклог

- Перенесите незавершённые истории в следующий спринт или обратно в бэклог.
- PO пересматривает приоритеты.
- Команда проводит краткий refinement.

**В отчёт:** итоги ревью (таблица планировалось/сделано), текст ретроспективы.

## Шаг 10. Релиз

### 10.1. Создайте Milestone

1. Откройте **Issues → Milestones → New milestone**.
2. Название: `v0.1.0`, описание: «MVP: регистрация, просмотр и бронирование аудиторий», дата — условная.
3. Добавьте в Milestone все Issues релиза (в каждом Issue справа → **Milestone**).

> Если вы использовали поле `Release` в проекте — оно дублирует Milestone. В реальной практике достаточно одного механизма; в учебной работе используйте оба, чтобы увидеть разницу.

### 10.2. Проверьте готовность

Перед релизом пройдите чек-лист:

- [ ] Все Issues Milestone `v0.1.0` закрыты (или переведены в следующий релиз с обоснованием).
- [ ] Выполнены критерии DoD.
- [ ] README актуален.
- [ ] Основная ветка (`main`) стабильна.

Запишите, **сколько Issues и SP** вошло в релиз, а сколько отложено.

### 10.3. Выпустите релиз

1. Откройте **Code → Releases → Draft a new release** (справа на странице репозитория: **Releases → Create a new release**).
2. В поле **Choose a tag** введите `v0.1.0` и выберите **Create new tag on publish**.
3. Target — `main`.
4. Название: `v0.1.0 — MVP`.
5. Нажмите **Generate release notes** — GitHub соберёт список Pull Requests автоматически. Отредактируйте текст, сделайте его понятным пользователю:

```markdown
## Что нового
- Добавлена регистрация и вход
- Можно просматривать список аудиторий

## Известные ограничения
- Уведомления по e-mail появятся в v0.2.0
```

6. Нажмите **Publish release**.

### 10.4. Закройте Milestone

Откройте Milestone и нажмите **Close milestone**.

**Проверьте:** в разделе Releases появилась запись `v0.1.0` с тегом и описанием.

**В отчёт:** ссылка на релиз; скриншот Milestone с прогрессом.

## Шаг 11. Расчёт метрик

Теперь рассчитаем метрики команды. Используем **ваши данные** и **учебный набор данных** (приведён ниже), чтобы получить достаточно измерений.

### 11.1. Velocity

**Формула:** Velocity спринта = сумма Estimate **полностью завершённых** историй спринта.

**Как получить из проекта:**

1. В представлении Backlog или Table включите **Group by → Iteration** и **Field sum → Estimate**.
2. Добавьте фильтр `status:Done` — увидите сумму SP по каждой итерации.

**Учебные данные прошлых спринтов команды-«эталона»:**

| Спринт | Запланировано (SP) | Завершено (SP) |
|---|---|---|
| Спринт A | 20 | 14 |
| Спринт B | 16 | 15 |
| Спринт C | 16 | 18 |
| Спринт D | 18 | 17 |

**Задания:**

1. Определите Velocity каждого спринта. Добавьте **ваш Спринт 1** как пятую строку.
2. Рассчитайте **среднюю Velocity** по последним трём спринтам.
3. Найдите **минимальную и максимальную** Velocity.
4. Оцените **точность планирования**: `завершено / запланировано × 100 %` для каждого спринта.

### 11.2. Прогноз релиза через Velocity

**Условие:** в бэклоге осталось **80 SP** до релиза `v1.0.0`.

Рассчитайте количество спринтов:

- по средней Velocity последних трёх спринтов;
- по минимальной Velocity;
- по максимальной Velocity.

Сформулируйте прогноз **диапазоном** («от N до M спринтов, наиболее вероятно K»).

### 11.3. Lead Time и Cycle Time

**Формулы:**

```
Lead Time  = дата завершения − дата создания
Cycle Time = дата завершения − дата начала работы
Ожидание   = Lead Time − Cycle Time
```

**Как получить из проекта:**

- **Created** — дата создания Issue (колонка Created at / видна в карточке и доступна как поле, если включено в представлении);
- **Started**, **Finished** — ваши поля.

**Учебные данные (даты условные, в формате ДД.ММ):**

| Issue | Создан | Начат | Завершён |
|---|---|---|---|
| #1 | 01.09 | 02.09 | 05.09 |
| #2 | 01.09 | 03.09 | 09.09 |
| #3 | 01.09 | 05.09 | 07.09 |
| #4 | 02.09 | 06.09 | 12.09 |
| #5 | 02.09 | 09.09 | 13.09 |
| #6 | 03.09 | 10.09 | 11.09 |
| #7 | 03.09 | 11.09 | 16.09 |
| #8 | 04.09 | 12.09 | 18.09 |

**Задания:**

1. Для каждой задачи рассчитайте Lead Time, Cycle Time и время ожидания в днях.
2. Найдите **среднее** и **медиану** Lead Time и Cycle Time.
3. Постройте простую столбчатую диаграмму Cycle Time по задачам (в Excel/Google Sheets или в GitHub Insights — см. ниже).
4. Определите, какая часть Lead Time приходится на ожидание (в процентах). Сделайте вывод.

Затем рассчитайте те же метрики для **ваших** задач из Спринта 1.

### 11.4. Throughput и закон Литтла

1. Посчитайте **Throughput** — сколько задач ваша команда завершила за Спринт 1.
2. Определите **среднее WIP** (сколько карточек в среднем находилось в `In progress` в разные моменты).
3. Проверьте закон Литтла: `Cycle Time ≈ WIP / Throughput` (пересчитайте Throughput на один и тот же период времени, например, в «задач в день»). Сопоставьте с вашим фактическим Cycle Time и объясните расхождение.

### 11.5. Графики в GitHub Insights

1. В проекте нажмите значок **Insights** (график) вверху справа.
2. Откройте готовый график **Burn up** (если доступен) — он показывает, как растёт число завершённых элементов по итерациям.
3. Нажмите **New chart** и создайте собственные графики:

| График | Настройки |
|---|---|
| «SP по статусам» | Layout: **Stacked bar**; X-axis: **Iteration**; Group by: **Status**; Y-axis: **Sum of Estimate** |
| «Задачи по приоритетам» | Layout: **Bar**; X-axis: **Priority**; Y-axis: **Count of items** |
| «Рост бэклога» | Layout: **Line** / Historical (если доступно); Y-axis: **Count of items** |

4. Сохраните графики (**Save changes**). Сделайте скриншоты.

### 11.6. Выводы по метрикам

Ответьте письменно (3–6 предложений на пункт):

1. Какая у команды Velocity и насколько она стабильна?
2. Что показывает разница между Lead Time и Cycle Time?
3. Где в процессе возникают задержки (подсказка: сравните время `In progress` и `In review`)?
4. Какие два конкретных улучшения вы предлагаете для следующего спринта и как проверите их эффект по метрикам?

## Содержание отчёта

Отчёт оформляется в Markdown (можно в виде `docs/report.md` в репозитории) или PDF. Структура:

1. **Титульная информация:** ФИО, группа, команда, роли, дата.
2. **Ссылки:** на репозиторий, проект GitHub, релиз.
3. **Цель и описание проекта.**
4. **Бэклог:** список историй (таблица), скриншот проекта.
5. **Оценка:** выбранная эталонная история, таблица Planning Poker, выводы (где были наибольшие расхождения и почему).
6. **Приоритизация:** таблица MoSCoW, состав релиза `v0.1.0`.
7. **Планирование Спринта 1:** цель, ёмкость, состав, скриншот.
8. **Результаты спринта:** запланировано / выполнено, скриншоты доски, ссылки на Pull Requests.
9. **Ретроспектива:** текст из Issue `Retro Sprint 1`.
10. **Релиз:** Release Notes, ссылка на тег.
11. **Метрики:** расчёты Velocity, Lead Time, Cycle Time, Throughput, прогноз, графики.
12. **Выводы:** что получилось, что вызвало трудности, чему научились.
