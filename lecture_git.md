## 2. Зачем нужен Git-воркфлоу

**Git-воркфлоу** — это **договорённость команды о том, как работать с репозиторием**: где создавать ветки, как называть коммиты, как попадает код в основную ветку и кто его проверяет.

Git сам по себе **ничего не запрещает**. Без правил возникают типичные проблемы:

- несколько человек правят одни и те же файлы, и возникают тяжёлые конфликты слияния;
- в `main` попадает неработающий код;
- в истории десятки коммитов вида `fix`, `fix2`, `asdf`;
- непонятно, кто и зачем изменил код;
- ревью делается формально или не делается совсем.

Хороший воркфлоу даёт:

1. **Предсказуемость:** каждый знает, что делать.
2. **Качество:** проверки происходят до того, как код попал в общую ветку.
3. **Скорость:** меньше конфликтов и ручной координации.
4. **Прозрачность:** по истории понятно, что и почему менялось.

## 3. Популярные модели ветвления

### 3.1. Git Flow

Модель с несколькими долгоживущими ветками.

```
main      ●───────────────────●────────────●   ← только релизы (теги)
           \                 / \          /
hotfix      \               /   ●────────●
             \             /
release       \       ●───●
               \     / 
develop  ●──────●───●─────●────────────────●   ← интеграционная ветка
          \    /     \   /
feature    ●──●       ●─●
```

| Ветка | Назначение |
|---|---|
| `main` | Стабильный код, каждый коммит — релиз |
| `develop` | Интеграция готовых функций |
| `feature/*` | Разработка новой функции |
| `release/*` | Подготовка релиза |
| `hotfix/*` | Срочное исправление в продакшене |

**Плюсы:** чёткая структура, удобно для продуктов с редкими версионными релизами (десктопное ПО, мобильные приложения, библиотеки с поддержкой нескольких версий).
**Минусы:** сложно, много долгоживущих веток, тяжёлые слияния, медленная обратная связь, плохо сочетается с непрерывной поставкой (CI/CD).

### 3.2. GitHub Flow

Упрощённая модель: одна основная ветка `main`, всё остальное — короткие ветки под задачи.

```
main    ●────●─────────●─────────●
         \  /           \       /
branch    ●●             ●─●──●   ← Pull Request, ревью, слияние
```

Шаги: создать ветку от `main` → коммиты → Pull Request → ревью и проверки → слияние в `main` → деплой.

**Плюсы:** просто, подходит для веб-сервисов и непрерывной поставки.
**Минусы:** ветки могут жить долго, если команда не дисциплинирована.

### 3.3. Trunk-Based Development (TBD)

**Trunk** («ствол») — основная ветка (`main`). Все разработчики интегрируют изменения в неё **очень часто** — минимум раз в день. Подробнее — в следующем разделе.

### 3.4. Сравнение

| Критерий | Git Flow | GitHub Flow | Trunk-Based |
|---|---|---|---|
| Долгоживущие ветки | `main`, `develop` | `main` | только `main` |
| Время жизни feature-ветки | дни–недели | часы–дни | **часы – 1–2 дня** |
| Сложность | высокая | низкая | низкая |
| Частота интеграции | редкая | средняя | **высокая** |
| Требования к автотестам | средние | высокие | **очень высокие** |
| Релизы | по версиям | непрерывные | непрерывные или по тегам |
| Подходит для | версионных продуктов | веб-сервисов | команд с зрелым CI/CD |

> Важно: **нет «лучшей на все случаи» модели.** Выбор зависит от продукта, команды и зрелости процессов.

## 4. Trunk-Based Development

### 4.1. Основные принципы

1. **Одна основная ветка** (`main`/`trunk`) — всегда в рабочем состоянии.
2. **Короткоживущие ветки:** от нескольких часов до 1–2 дней.
3. **Небольшие изменения:** мелкие Pull Request легче ревьюить и меньше ломают.
4. **Частая интеграция:** вливаем в `main` как минимум раз в день.
5. **Автоматические проверки** (тесты, линтеры) на каждом изменении.
6. **Незавершённая функциональность скрыта** от пользователей (feature flags).

### 4.2. Два варианта TBD

**А. Для маленьких команд:** разработчики коммитят прямо в `main` (с проверками). Практически используется редко и требует очень высокой зрелости.

**Б. Для масштабируемых команд (рекомендуется для учебной работы):** короткоживущие ветки + Pull Request + быстрое ревью + слияние (лучше `squash merge`).

```
main  ●────●────●────●────●────●────●
       \  /      \  /      \  /
        ●●        ●●        ●●        ← ветки живут часы, а не недели
```

### 4.3. Как быть с незавершённой функцией: Feature Flags

Если функция большая, её нельзя закончить за день. Вместо долгой ветки:

1. Разбиваем функцию на мелкие шаги.
2. Каждый шаг вливаем в `main` часто.
3. Скрываем недоделанный код за **флагом функции** (feature flag / feature toggle).

Пример на JavaScript:

```js
const FEATURES = {
  newCheckout: process.env.FEATURE_NEW_CHECKOUT === 'true',
};

if (FEATURES.newCheckout) {
  renderNewCheckout();   // новая, недоделанная версия
} else {
  renderOldCheckout();   // старая, стабильная
}
```

Пока флаг выключен, пользователи не видят изменений, а код уже интегрирован и не конфликтует с чужими правками. Когда функция готова — флаг включают, а потом удаляют (**флаги нельзя оставлять навсегда**, это «технический долг»).

### 4.4. Что нужно, чтобы TBD работал

| Условие | Зачем |
|---|---|
| Автотесты и CI | Быстро находить поломки в `main` |
| Малые изменения | Простое ревью |
| Быстрое ревью (в течение нескольких часов) | Ветки не «зависают» |
| Feature flags | Скрывать незавершённое |
| Защита `main` | Исключить прямые «сломанные» коммиты |
| Локальные проверки (hooks) | Не засорять CI очевидными ошибками |

### 4.5. Релизы в TBD

- **Непрерывная поставка:** каждый коммит в `main`, прошедший проверки, можно выпускать.
- **Релизные теги:** при необходимости ставим тег (`v1.4.0`) на нужный коммит в `main`.
- **Релизные ветки** (по необходимости): короткая ветка `release/1.4` создаётся **от** `main` и содержит только исправления критических ошибок, которые затем «переносятся» (cherry-pick) обратно в `main`. Разработка новых функций в релизных ветках не ведётся.

### 4.6. Типичный рабочий цикл в TBD

```bash
# 1. Обновляем main
git switch main
git pull --rebase

# 2. Создаём короткую ветку
git switch -c feat/123-search-filter

# 3. Работаем, делаем небольшие коммиты
git add .
git commit -m "feat(search): add filter by date"

# 4. Перед отправкой подтягиваем свежий main
git fetch origin
git rebase origin/main

# 5. Отправляем и открываем Pull Request
git push -u origin feat/123-search-filter

# 6. После ревью и зелёного CI — слияние (squash), ветка удаляется
```

## 5. Соглашения: имена веток и сообщения коммитов

### 5.1. Имена веток

Формат: `<тип>/<номер-задачи>-<краткое-описание>`

| Тип | Пример |
|---|---|
| `feat` | `feat/42-user-login` |
| `fix` | `fix/57-null-pointer-on-save` |
| `docs` | `docs/60-readme-update` |
| `refactor` | `refactor/71-split-service` |
| `chore` | `chore/80-update-deps` |

Правила: латиница, строчные буквы, слова через дефис, коротко и по делу.

### 5.2. Conventional Commits

**Conventional Commits** — стандарт оформления сообщений коммитов:

```
<тип>(<область>): <краткое описание>

[необязательное тело]

[необязательный подвал: BREAKING CHANGE, ссылка на задачу]
```

Основные типы:

| Тип | Значение |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения документации |
| `style` | Форматирование (без изменения логики) |
| `refactor` | Рефакторинг без новых функций и исправлений |
| `test` | Добавление или правка тестов |
| `chore` | Служебные изменения (зависимости, конфиги) |
| `ci` | Изменения в CI |
| `perf` | Улучшение производительности |

Примеры **хороших** сообщений:

```
feat(auth): add password reset by email
fix(cart): prevent negative item quantity
docs: add setup instructions to README
```

Примеры **плохих** сообщений: `fix`, `update`, `правки`, `asdf`, `final_v2`.

Преимущества: читаемая история, автоматическая генерация changelog и номеров версий (SemVer), понятность для всех.

### 5.3. Правила хорошего коммита

- **Один коммит — одна логическая правка.**
- Описание в повелительном наклонении: «add», «fix», «remove».
- Не коммитить секреты, большие бинарные файлы, артефакты сборки.
- Не смешивать форматирование и изменение логики в одном коммите.

## 6. Git hooks: что это и как работают

### 6.1. Определение

**Git hooks** («крючки») — скрипты, которые Git **автоматически запускает при определённых событиях** (перед коммитом, перед отправкой и т. д.). Если скрипт завершается с **ненулевым кодом**, Git **прерывает операцию**.

Хуки лежат в каталоге `.git/hooks/` каждого репозитория.

```
git commit ──► [pre-commit] ──► [prepare-commit-msg] ──► [commit-msg] ──► коммит создан
                   │                                          │
         проверка кода провалена?                 сообщение не по правилам?
                   ▼                                          ▼
              коммит отменён                             коммит отменён
```

### 6.2. Основные хуки

| Хук | Когда срабатывает | Типичное использование |
|---|---|---|
| `pre-commit` | До создания коммита | Линтер, форматирование, быстрые проверки |
| `prepare-commit-msg` | До открытия редактора сообщения | Подстановка шаблона |
| `commit-msg` | После ввода сообщения | Проверка формата сообщения (Conventional Commits) |
| `post-commit` | После коммита | Уведомления |
| `pre-push` | Перед `git push` | Запуск тестов |
| `pre-rebase` | Перед rebase | Защита от rebase опубликованных веток |
| `post-merge` / `post-checkout` | После слияния/переключения | Установка зависимостей |

### 6.3. Простейший хук вручную

Файл `.git/hooks/pre-commit` (без расширения, должен быть исполняемым):

```bash
#!/bin/sh
echo "Запускаю проверки..."
npm run lint || exit 1
```

```bash
chmod +x .git/hooks/pre-commit
```

### 6.4. Проблема ручных хуков

Папка `.git/hooks/` **не попадает в репозиторий**: её содержимое не хранится в Git и не передаётся при `git clone`. Поэтому «ручные» хуки у каждого разработчика свои, и о них можно забыть.

**Решение:** использовать инструменты, которые **хранят конфигурацию хуков в репозитории** и устанавливают их автоматически:

- **Husky** (+ lint-staged) — для JavaScript/TypeScript-проектов;
- **pre-commit** (фреймворк) — для Python и многоязычных проектов;
- встроенный вариант: `git config core.hooksPath .githooks` (хуки лежат в папке репозитория, но установку нужно выполнять каждому).

## 7. Husky и lint-staged (экосистема JavaScript)

### 7.1. Роли инструментов

| Инструмент | Что делает |
|---|---|
| **Husky** | Управляет Git hooks: хранит их в папке `.husky/` и подключает автоматически после `npm install` |
| **lint-staged** | Запускает команды **только для файлов, добавленных в индекс** (staged) — быстро |
| **ESLint** | Ищет ошибки и плохие практики в коде |
| **Prettier** | Автоматически форматирует код |
| **commitlint** | Проверяет сообщения коммитов по Conventional Commits |

### 7.2. Почему lint-staged

Если на каждый коммит проверять **весь проект**, хук будет работать минутами, и разработчики начнут его обходить. lint-staged передаёт линтеру **только изменённые файлы** — проверка занимает секунды.

### 7.3. Схема работы

```
git commit
   │
   ▼
.husky/pre-commit  ──►  npx lint-staged
                              │
                              ├─ *.js  → eslint --fix → prettier --write
                              └─ *.md  → prettier --write
                              │
                    ошибка? ──┴──► коммит отменён
   │
   ▼
.husky/commit-msg  ──►  commitlint --edit $1
                              │
                    формат неверный? → коммит отменён
```

### 7.4. Установка (ориентировочно)

```bash
npm install --save-dev husky lint-staged eslint prettier \
  @commitlint/cli @commitlint/config-conventional

npx husky init        # создаёт .husky/pre-commit и добавляет "prepare": "husky" в package.json
```

Фрагмент `package.json`:

```json
{
  "scripts": {
    "prepare": "husky",
    "lint": "eslint .",
    "test": "node --test"
  },
  "lint-staged": {
    "*.js": ["eslint --fix", "prettier --write"],
    "*.{json,md,yml}": ["prettier --write"]
  }
}
```

Скрипт `prepare` выполняется автоматически после `npm install`, поэтому **каждый, кто клонирует репозиторий и ставит зависимости, получает хуки без дополнительных действий**.

Файл `.husky/pre-commit`:

```sh
npx lint-staged
```

Файл `.husky/commit-msg`:

```sh
npx --no -- commitlint --edit "$1"
```

> Детальная пошаговая настройка — в практической работе.

## 8. Фреймворк pre-commit (экосистема Python и не только)

### 8.1. Идея

**pre-commit** — фреймворк на Python для управления хуками. Конфигурация лежит в файле `.pre-commit-config.yaml` в репозитории, а сами проверки подключаются как **готовые «репозитории хуков»** из интернета. Работает с любым языком.

### 8.2. Пример конфигурации

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0                      # фиксируем версию
    hooks:
      - id: trailing-whitespace      # лишние пробелы в конце строк
      - id: end-of-file-fixer        # перевод строки в конце файла
      - id: check-yaml               # корректность YAML
      - id: check-added-large-files  # запрет больших файлов
      - id: detect-private-key       # поиск приватных ключей

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.5.0
    hooks:
      - id: ruff                     # линтер Python
        args: [--fix]
      - id: ruff-format              # форматирование
```

> Номера версий (`rev`) приведены для примера; актуальные берутся со страниц репозиториев хуков или командой `pre-commit autoupdate`.

### 8.3. Использование

```bash
pip install pre-commit
pre-commit install                   # устанавливает хук в .git/hooks
pre-commit install --hook-type commit-msg   # (опционально) хук для сообщений коммитов
pre-commit run --all-files           # запустить на всём проекте
pre-commit autoupdate                # обновить версии хуков
```

Каждый новый участник выполняет `pre-commit install` один раз после клонирования (это стоит написать в README).

### 8.4. Husky против pre-commit

| Критерий | Husky + lint-staged | pre-commit |
|---|---|---|
| Основная экосистема | Node.js | Python, мультиязычные проекты |
| Конфигурация | `package.json`, `.husky/*` | `.pre-commit-config.yaml` |
| Автоустановка | да (через `prepare`) | нет, нужен `pre-commit install` |
| Изоляция окружения | использует локальные пакеты проекта | сам скачивает и изолирует хуки |
| Готовые проверки | пишете сами из npm-пакетов | большая библиотека готовых хуков |

## 9. Что проверять в хуках, а что в CI

### 9.1. Главный принцип

> **Хуки — для быстрой обратной связи разработчику. CI — для гарантии качества.**

Локальные хуки **можно обойти**: `git commit --no-verify` пропускает `pre-commit` и `commit-msg`. Хуки можно отключить или не установить. Поэтому те же проверки **обязательно дублируются в CI**, а ветка `main` защищается правилами, не позволяющими влить код без зелёного CI.

### 9.2. Распределение проверок

| Проверка | `pre-commit` | `pre-push` | CI |
|---|:---:|:---:|:---:|
| Форматирование (Prettier, Black) | ✅ | | ✅ |
| Линтер (ESLint, Ruff) | ✅ (только staged) | | ✅ (весь проект) |
| Формат сообщения коммита | ✅ (`commit-msg`) | | ✅ |
| Поиск секретов/ключей | ✅ | | ✅ |
| Быстрые unit-тесты | | ✅ | ✅ |
| Полный набор тестов | | | ✅ |
| Сборка, интеграционные тесты | | | ✅ |
| Проверка безопасности зависимостей | | | ✅ |

**Правило скорости:** `pre-commit` должен выполняться **за секунды** (1–10 с). Если дольше — разработчики начнут его обходить.

### 9.3. Чего не делать в хуках

- Не запускать долгие тесты в `pre-commit`.
- Не менять файлы «втихую» без понятного вывода (автоформатирование допустимо, но результат должен быть виден).
- Не делать сетевые запросы, которые могут падать из-за интернета.
- Не считать хуки защитой от злоумышленника: это помощь честному разработчику.

## 10. Pull Request и код-ревью

### 10.1. Что такое Pull Request

**Pull Request (PR)** (в GitLab — Merge Request) — запрос на слияние ветки в основную. Это не просто «кнопка слияния», а **место обсуждения и проверки** изменений:

- описание: что и зачем сделано;
- diff изменений;
- автоматические проверки (CI);
- комментарии ревьюеров;
- решение: одобрить, запросить правки или отклонить.

### 10.2. Зачем нужно код-ревью

1. **Поиск ошибок** до попадания в `main`.
2. **Обмен знаниями** — команда знает, как устроен код.
3. **Единый стиль и качество.**
4. **Наставничество** — особенно для начинающих.
5. **Коллективная ответственность** за код.

### 10.3. Хороший Pull Request

| Свойство | Рекомендация |
|---|---|
| Размер | Небольшой: ориентир — до ~200–400 строк изменений |
| Цель | Одна задача — один PR |
| Описание | Что, зачем, как проверить |
| Ссылка на задачу | `Closes #42` |
| Состояние CI | Зелёное до запроса ревью |
| Скриншоты | Для визуальных изменений |

### 10.4. Хорошее ревью

**Автору:**
- сам прочитать свой diff перед отправкой;
- отвечать на комментарии спокойно и по существу;
- не воспринимать замечания как личную критику.

**Ревьюеру:**
- реагировать быстро (в TBD — в течение нескольких часов);
- критиковать **код, а не человека**;
- формулировать как вопрос или предложение: «Может, вынести это в функцию?»;
- разделять **блокирующие** замечания и **необязательные** (nit: …);
- отмечать и удачные решения.

### 10.5. Стратегии слияния

| Стратегия | Что делает | Когда использовать |
|---|---|---|
| **Merge commit** | Сохраняет все коммиты ветки + создаёт коммит слияния | Когда важна полная история ветки |
| **Squash and merge** | Все коммиты ветки → один коммит в `main` | **Рекомендуется для TBD**: чистая линейная история |
| **Rebase and merge** | Переносит коммиты ветки на `main` без коммита слияния | Когда коммиты в ветке аккуратные |

## 11. Шаблон PR и чек-лист ревью

### 11.1. Зачем нужен шаблон

Шаблон Pull Request:

- **напоминает автору** о важных шагах (тесты, документация);
- **единообразно структурирует** описание;
- **ускоряет ревью**, потому что у ревьюера сразу есть контекст.

В GitHub шаблон хранится в файле `.github/pull_request_template.md` и автоматически подставляется в описание нового PR.

### 11.2. Пример шаблона

```markdown
## Описание
<!-- Что изменено и зачем? Кратко. -->

## Тип изменения
- [ ] feat — новая функциональность
- [ ] fix — исправление ошибки
- [ ] refactor — рефакторинг
- [ ] docs — документация
- [ ] chore / ci — служебные изменения

## Связанная задача
Closes #

## Как проверить
1. ...
2. ...

## Чек-лист автора
- [ ] Ветка короткая, от актуального `main`
- [ ] Код соответствует стилю проекта, хуки и линтер проходят
- [ ] Добавлены или обновлены тесты
- [ ] Все тесты проходят локально
- [ ] Документация/README обновлены (если нужно)
- [ ] Нет секретов, паролей, отладочного кода
- [ ] Незавершённая функциональность скрыта за feature flag

## Чек-лист ревьюера
- [ ] Изменение решает поставленную задачу
- [ ] Код понятен и читаем
- [ ] Нет очевидных ошибок и пропущенных граничных случаев
- [ ] Тесты достаточны и осмысленны
- [ ] Нет проблем с безопасностью (ввод данных, секреты)
- [ ] Нет лишних изменений, не относящихся к задаче

## Скриншоты (если применимо)
```

### 11.3. Другие файлы в `.github/`

| Файл | Назначение |
|---|---|
| `pull_request_template.md` | Шаблон Pull Request |
| `ISSUE_TEMPLATE/*.md` | Шаблоны Issues |
| `CODEOWNERS` | Кто автоматически назначается ревьюером на какие файлы |
| `workflows/*.yml` | Конфигурации GitHub Actions (CI) |

Пример `CODEOWNERS`:

```
# Все файлы — по умолчанию ревьюит команда
*             @org/dev-team

# Документацию — только технический писатель
/docs/        @ivanov
```

### 11.4. Чек-лист ревью по уровням (для самостоятельной работы)

| Уровень | Что проверить |
|---|---|
| Корректность | Делает ли код то, что задумано? Обработаны ли ошибки и пустые значения? |
| Читаемость | Понятны ли имена? Нет ли дублирования? Не слишком ли длинные функции? |
| Тесты | Есть ли тесты на новую логику и граничные случаи? |
| Безопасность | Нет ли секретов в коде? Проверяется ли пользовательский ввод? |
| Совместимость | Не ломает ли изменение существующий функционал и API? |
| Производительность | Нет ли очевидно неэффективных мест (запросы в цикле)? |
| Документация | Обновлены ли README, комментарии, changelog? |

## 12. Защита основной ветки

Чтобы TBD работал, `main` должна быть **защищена от прямых небезопасных изменений**. В GitHub это настраивается через **Branch protection rules** (Settings → Branches) или **Rulesets**.

Рекомендуемые правила для `main`:

| Правило | Смысл |
|---|---|
| **Require a pull request before merging** | Запрет прямых коммитов в `main` |
| **Require approvals (≥ 1)** | Обязательное ревью |
| **Require status checks to pass** | CI должен быть зелёным |
| **Require branches to be up to date** | Ветка актуальна относительно `main` |
| **Require conversation resolution** | Все комментарии закрыты |
| **Require linear history** | Только squash/rebase, без «ёлочки» merge-коммитов |
| **Do not allow force pushes** | Запрет перезаписи истории |
| **Automatically delete head branches** | Удалять ветку после слияния |

### Пример минимального CI (GitHub Actions)

Файл `.github/workflows/ci.yml`:

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
```

Те же проверки, что и в хуках, **повторяются в CI** — это страховка на случай обхода хуков.

## 13. Типичные ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| Долгоживущие ветки в TBD | Тяжёлые конфликты, «большой взрыв» при слиянии | Дробить работу, интегрировать ежедневно, использовать feature flags |
| Огромные Pull Request | Ревью формальное или откладывается | Небольшие PR по одной задаче |
| Тяжёлые тесты в `pre-commit` | Хук обходят через `--no-verify` | Быстрые проверки в `pre-commit`, тесты — в `pre-push` и CI |
| Положиться только на хуки | Проверки можно обойти | Дублировать в CI, защитить `main` |
| Хуки не в репозитории | У коллег нет проверок | Husky с `prepare` или pre-commit с инструкцией в README |
| Прямые коммиты в `main` | Сломанная основная ветка | Branch protection |
| Забытые feature flags | Мёртвый код и усложнение | Удалять флаги после включения функции |
| Формальный шаблон PR (чек-лист всегда «галочки не глядя») | Нет пользы | Обсуждать на ревью, сокращать чек-лист до реально значимых пунктов |
| Коммиты `fix`, `update` | Нечитаемая история | Conventional Commits + commitlint |
| `git push --force` в общую ветку | Потеря чужой работы | Запретить; использовать `--force-with-lease` только на своей ветке |

## 14. Итоги, вопросы, литература

### 14.1. Ключевые идеи

1. Git-воркфлоу — это **командная договорённость**, а не возможность Git.
2. **Trunk-Based Development**: одна основная ветка, короткие ветки, частая интеграция, feature flags, сильные автотесты.
3. **Git hooks** запускают проверки автоматически; **Husky** и **pre-commit** хранят конфигурацию хуков в репозитории.
4. **lint-staged** проверяет только изменённые файлы — быстро.
5. **commitlint** и Conventional Commits делают историю читаемой.
6. Хуки можно обойти, поэтому **CI и защита `main` обязательны**.
7. **Шаблон PR с чек-листом** задаёт стандарт качества ревью.

### 14.3. Мини-задачи

**Задача 1.** Определите, какие сообщения коммитов соответствуют Conventional Commits:
а) `fix bug`; б) `feat(cart): add promo code field`; в) `Update README`; г) `docs: describe branch naming`.

**Задача 2.** Разработчик создал ветку `feature/big-refactoring` и работает над ней уже три недели. Какие проблемы ожидаются и что предложить?
*(Ответ: конфликты и «взрыв» при слиянии, поздняя обратная связь. Разбить работу на мелкие шаги, вливать в `main` ежедневно, скрывать незавершённое за feature flag.)*
